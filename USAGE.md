# Using the wiki-engine loop

Day-to-day guide for **the wiki-engine loop** — a curated-memory engine for coding agents. A git-versioned personal wiki (your **vault**) plus this **engine** (pinned per vault as `engine/`) that gives it skills, deterministic tools, and a capture → recall → promote memory loop.

For the *spec* (node model, conventions, lifecycle) see `SCHEMA.md`. For *first-time setup* see `README.md`. This doc is how you drive it once it exists.

## The mental model — one loop

```
   auto-capture ──▶ raw/sessions ──▶ semantic recall ──▶ review & promote ──▶ memory/
   (SessionEnd hook)   (metadata)      (bge-base RAG)      (you approve)      (curated)
        ▲                                                                        │
        └──────────────────────  next session recalls it  ◀─────────────────────┘
```

- **Capture** is cheap, deterministic, automatic (a hook). **Curation** (promote) is judgment, in-session, human-gated. **Recall** makes both findable so you *just prompt*.
- Curated `memory/` outranks raw in recall, so the auto-captured pile never drowns the good stuff.

## A day in the loop

**Session start** — the `wiki-context` skill runs: checks engine freshness, reads `index.md`, **semantically recalls** the pages relevant to your prompt (no need to name them), and offers to **review-and-promote** any raw captured since last time. You just start describing the task.

**While working** — recall surfaces the relevant curated pages. To pull a repo's context in, invoke `wiki-repo` (it ingests/refreshes one repo page with git-ref provenance). Otherwise just work.

**Session end** — if the SessionEnd hook is wired, `rag-capture.sh` auto-records session metadata to `raw/sessions/`. When a durable fact/decision/lesson emerged, run the `checkpoint` skill: it distills keepers into `memory/`, updates the active project page + `log.md`, prunes promoted raw, lints, and re-indexes for recall.

## Skills (in-session; run in a Claude Code session with `$WIKI_PATH` set)

- **`wiki-context`** — session-start router: freshness check → recall → review-and-promote. The token-saver; load only what's relevant.
- **`wiki-repo`** — ingest or refresh ONE repo page with git provenance (a *freshness* refresh when the sha moved).
- **`verify`** — run a *correctness* pass on repo pages: confirm the page against the real repo at its recorded sha, fix drift (and the source repo if it originated there), stamp the `verified:` signal. Complements `wiki-repo` (freshness) — a page can be fresh yet wrong.
- **`checkpoint`** — end-of-session: distill memory, update project + log, prune raw, lint, re-index, then **offer** the skill-mining pass (§6). It does not run it. The offer comes last, after the commit and integrate, for two reasons: mining judges recurrence across weeks and has nothing to read until this session's notes have landed, and §0's worktree is retired by then, so a run that accepts opens its own rather than writing into a tree this pass still holds. **Deferring writes nothing** and loses nothing — the evidence is the committed notes, which any later run re-derives from. Mining used to run automatically on the argument that it is cheap in steady state; it is, in *tokens*, but the cost that lands on the operator is a set of develop/discard/defer decisions injected at the moment they are closing out unrelated work, and a `develop` verdict begins a chain (author a skill → write an eval → fix the fixture) they should start deliberately. **There are now zero edges between the two skills**, in either direction — stronger than the one-way edge it replaces, and the reason the verdict write could move to the skill that produces them.
- **`prove-the-test-can-fail`** — run a newly written check against a deliberately broken subject and prove it goes red, rather than reading it and assuming. **Breaks the SUBJECT, never the assertion** — deleting an assertion and watching the complaint stop proves only that you deleted it; the question is whether the check notices a real violation. Requires all three of a non-zero exit, a message naming the subject, and proof the mutation took effect, because each has failed alone here: a step that never ran reports nothing and reads as a pass, and the v1.62.0 fixture passed trivially when the step it depended on silently did nothing. Then restores by explicit path, requires green again (a check red on a mutation *and* red after restore is stuck, not working), and finally runs a **near-miss** — something that merely resembles the subject — which the check must reject. That last step is the one the obvious procedure omits and the one this repo keeps needing: `drain` was "documented" by *drainable*, a `skill-candidates-meta` tag satisfied a query for `skill-candidate`, and `ci` matched inside "de**ci**sion". **Refuses outright on a dirty working tree**, since restore is `git checkout -- <path>` and with uncommitted work in the way, restoring correctly and clobbering silently are the same command. Reports both exit statuses and the red message as evidence; "it passed" is not a report. Distinct from `drain`, which carries red-before-green as one clause of the release loop and only inside it.
- **`skill-candidates`** — the inverse of `checkpoint`: read the curated record back out (`memory/` notes, `log.md`, the session buffer) and report ranked **candidates** for new skills, each justified by dated evidence that the procedure actually repeated. The mining is read-only, but it **takes a worktree up front** because §7 records what the operator decided — taken at the start rather than at the end, so a run cannot discover halfway through that it has verdicts and nowhere safe to put them. The bar is three or more dated occurrences spread over time with stable steps and a varying subject — which exists because the end of a long session is exactly when novelty and recurrence feel identical, and the session in progress is the one input with no history behind it. **Two modes off one free signal** (no verdict note yet = never mined — asked of `^type:`/`^tags:`, never of the file text, since every note *about* the skill contains its name and would otherwise read as a verdict): the **first** run is a backlog drain over the whole record and *should* return many, since a vault that checkpointed for months without mining those notes has accumulated every procedure it repeated; every later run sweeps forward from the last verdict and should return none or one. The bar is identical in both — only the expected count changes, so an empty first run means the queries are wrong and a busy steady-state run means the vault went un-mined. Report everything clearing the bar, but recommend only a small set to **build** first, because eight skills authored in one sitting are eight thin ones. It checks overlap against every installed skill regardless of which repo ships it, then puts **every** candidate clearing the bar to the operator as an interactive **develop / discard / defer** choice — recommending, never deciding, since its ranking axes (recurrence × cost) measure whether the evidence is real and cannot see whether a skill is the right *form* at all; notes that already load on demand may cover the ground with nothing needing to fire. A discard captures the operator's **reason**, which is the whole value of the record. Question facilities cap questions per call, so it batches rather than truncating — a filtered list reported as the whole list is the failure it exists to avoid. It never writes a `SKILL.md`. It **does** write the verdicts, itself, as `type: decision` notes tagged `skill-candidate` — one commit, integrate, gc — so a discarded candidate is not rediscovered every run and a deferral is reconsidered once its count grows past the recorded one. That write moved here from `checkpoint` when the mining call was removed: with no caller left to hand verdicts to, a run that decided and wrote nothing would leave the vault indistinguishable from one never mined, since the two-modes check keys on a verdict note existing — so the next run would sweep the whole record and re-ask everything already settled. **Recording is not invoking**: it calls nothing, `checkpoint` calls nothing, and the cycle both files guard against needs an edge that no longer exists in either direction.
- **`wiki-onboard`** — one-time bulk seed of a fresh vault from existing native memory / repos / projects.
- **`wiki-adopt`** — idempotent adoption: scaffold a new vault **or** wire an already-cloned one, then seed. The front door on any new machine; safe to re-run.
- **`drain`** — the **engine-dev outer loop**: hold the whole work-list (open proposals, awaiting-merge and long-open pull requests, red CI, the gates, plus the consuming vault's pin, `verify-status` and `upkeep` queues) and run each item to *released and adopted* — reproduce at HEAD, judge the reporter's prescription against the mechanism, fix the **class** rather than the instance, drive the test red before green, fold the cycle's own drift into the same pass, then merge, tag, release, adopt and re-verify. It decides for itself what most loops stop to ask: release level (by this file's own SemVer rules), which shape to build including declining a reporter's suggestion *with the technical reason recorded*, the outcome and its reason, and provably-reversible cleanup. It stops only for a **breaking change**, **destroying work with no other copy**, a **taste call the code cannot settle**, or **a gate that would have to be weakened** to let the change land. Distinct from `engine-proposal`, which files or intakes exactly one report.
- **`update`** — engine-only machine catch-up: report + offer an engine version bump (`doctor`/`update.sh`), converge wiring (`wire-machine`), relink the engine's own skills. Generic — it never touches a consumer's separate skill repos; a consumer surfaces its own catch-up via a `session-checks.d` drop-in (below).
- **`crossover`** — migrate pages to a vault on another machine over a copy-paste channel (export → import → finalize), with sha256-verified soft-delete + tombstone reference sweep. The deliberate manual boundary crossing; nothing is deleted at the origin until a returned receipt's hash matches. Exports **one block per page** (paste them separately — total paste volume is what the channel drops); `import` accumulates the blocks into the batch.
- **`engine-proposal`** — genericize + boundary-scrub a *consumer* vault's engine-improvement idea **or defect report** into a self-contained, scan-verified handoff block for the engine-dev vault. **The route for a bug you hit while running the engine:** a consumer vault is where engine bugs surface and the one place that cannot fix them — editing the pinned `engine/` submodule in place is discarded by the next `update.sh`. A defect block separates the *observation* from the *suggested fix* (a reporter's fix can be wrong while the bug is real), names the failure shape — **fail-closed / fail-open / data-loss**, where fail-open is the severe one because it looks like success — and states the pinned version it still reproduces at, since a bug can be fixed incidentally and stay open on paper; and, at the engine-dev end, **intake**: design-review an arriving proposal before choosing a shape, then file the project with the accepted/rejected findings. Forward-only: originates a new idea (never a consumer node), so unlike `crossover` there is no integrity handshake and nothing is deleted — the only shared surface is the boundary gate. **The slug round-trips:** intake records the proposal in the engine's `PROPOSALS.md` on arrival and cites it as a `Proposal:` commit trailer when it ships, so `engine-proposal.sh status` can tell a consumer what shipped, what was declined *and why*, and what never arrived — the decline being the half that is otherwise invisible, since it produces no artifact in the engine at all.

## Commands (`bin/` — deterministic, no LLM; set `$WIKI_PATH` or pass `--wiki DIR`)

| Command | What it does |
| --- | --- |
| `recall.sh "query"` | Semantic search → `file:line` pointers into the real pages (`--json` for tools). |
| `rag-build.sh` | (Re)build the `.rag` index from the markdown. Incremental; run after big edits (`checkpoint` does it). |
| `rag-setup.sh` | Provision the self-contained `.rag/venv` CPU embedder (once per vault). `--force` to rebuild/change model. |
| `rag-capture.sh` | Deterministic session auto-capture → `raw/sessions/`. Safe to run from a SessionEnd hook. `WIKI_PATH` must be a **vault**, not just a directory that exists: the boundary stamped on each capture file is read from the vault's own `CLAUDE.md` and never defaulted, so a target with no readable declaration is **refused by name** rather than captured under a guess. |
| `doctor.sh` | Freshness/health report: engine + RAG deps (+ security) + model. Reports only. |
| `update.sh` | One-step apply: bump engine to latest tag (same-MAJOR), adopt, re-sync deps. Refuses MAJOR; stages, no commit. **Two trees, deliberately:** the pin is a gitlink and can only be staged in canonical, while a repo page is ordinary tracked content — so the page is written in the caller's worktree when they are in one, and when a commit in canonical would be **refused** (isolation on and a gate armed) it is **not written at all**, only printed for them to apply on their branch. The deferral follows the gate, not the worktree count: isolation being configured and a worktree being open are different states. The remedy commits the pointer **by path**, never `-am`, which in a shared checkout stages a concurrent session's modified files too. **Two phases, also deliberately:** the checkout replaces this script mid-run, so the apply half is handed to the copy just checked out through one sentinel-guarded re-exec (`UPDATE_CONTINUE_FROM`; `UPDATE_REEXEC=0` opts out) — otherwise a fix to `update.sh` lands one run late and the run says nothing about which copy acted. |
| `engine-version.sh` | Pinned vs latest engine tag (run by `wiki-context`). |
| `adopt.sh` | Ensure the vault has the engine's current node folders + run feature-adoption (after a pin bump). |
| `wire-machine.sh` | Idempotent converge — make THIS machine ready for the vault at `$WIKI_PATH`: submodule, skill links, `WIKI_PATH`, CLAUDE.md import, `.rag`, feature-adopt. `--check` previews. The "wire an existing clone" verb behind `wiki-adopt`. |
| `lint.sh` | Umbrella lint + write-time **gate** (memory + frontmatter + soft-wrap + catalog + boundary-present + provenance-present + link-integrity + foreign-boundary); `checkpoint`, a pre-commit hook, and vault CI all run it. |
| `vault-worktree.sh` | Concurrency machinery for multi-session/agent writing: `ensure` (per-session worktree), `guard` (refuse a commit in canonical — wire from `pre-commit`), `lease`/`peers` (advisory path declarations + live sessions), `claim` (advisory per-project presence, recorded on the same lease), `integrate` (locked rebase + fast-forward to `main`), `gc`/`list`. **`gc <path>`** retires one worktree now; **bare `gc`** sweeps stale worktrees, dead leases, **and orphan `wt/*` branches whose worktree is already gone** — those were previously evaluated only as a side effect of retiring a worktree, so nothing could ever reap them. A branch checked out anywhere is excluded by decision, and containment is judged by content, so every uncertain case keeps. **`ensure` never hands back a base silently behind the branch it claims to derive from:** reattaching to a surviving `wt/<session>` branch reports the distance from `origin/main` and how to rebase, and a branch whose content already landed (squash-merged included — judged by the same content test `gc` uses) is cut fresh off `origin/main` rather than reattached behind it. A **fresh cut** says so too when canonical `main` holds commits `origin/main` lacks — the ordinary commit-now-push-later case, which no fetch can surface and which corrupts *searches* rather than merges. See the Concurrency section below. |
| `lint-links.sh` | Link-integrity gate over content-node pages. A dangling `[[link]]` that **nearly** matches a real slug is an **error** (typo, or a slug left behind by a rename); one that matches nothing is a stub per `SCHEMA.md` and stays a warning. Links inside code spans/fences are documentation about the syntax, not links, and are ignored; targets listed in the vault's external-refs file (things that must never resolve here) are silent. |
| `engine-proposal.sh queue` | **The engine-dev work-list.** Lists open proposals in `proposals/`, oldest first (`--all` includes resolved ones), and prints the drain procedure beside the list so the two cannot drift apart. The one subcommand that does **not** take `--vault`: it runs in the engine repo, which is the only place it is useful. Without it the queue is a storage format rather than a work-list, and draining means `ls` plus grep. |
| `gen-proposals-ledger.sh` | Renders the `PROPOSALS.md` table from the `proposals/` queue directory, spliced between sentinels like the skills and projects catalogs. The **queue is the source of truth**; the table is derived, so the two cannot disagree — which was the real objection to keeping both. Refuses to write an empty ledger, and fails on a malformed entry (a `rejected`/`partially-accepted` with no reason, or a `slug:` disagreeing with its filename) rather than rendering a half-row. |
| `lint-summary-volatility.sh` | Gate on a project page's `summary:`: it must name **identity** (what the project is), not **state**. A summary holding a decaying fact goes false with no edit to the page, and the Projects buckets are generated from it — so the index advertises a state the page's own body contradicts. Skips `done` pages (frozen claims), flags an unknown/missing `status:` rather than exempting it. **Enforced via a content-hashed baseline**, not a warning: `lint.sh` is the pre-commit gate, so a warn on pre-existing offenders would be standing noise forever. Adoption seeds today's offenders; anything new errors. The baseline keys on `sha256(summary)`, so rewriting a summary drops its exemption. A **proxy**, not a decision procedure — recall is unbounded, and a clean run means "no listed marker", never "these summaries are stable". |
| `lint-proposals.sh` | CI gate over `PROPOSALS.md` and the `Proposal:` commit trailers: rows well-formed and unique, aliases resolvable and unchained, declines carrying a reason, every trailer having a row — and, the load-bearing one, and a citation being read LITERALLY wherever it appears, so GitHub's squash footer displacing it out of the final paragraph no longer matters (v1.42.1; misplacement is a note, not a failure, and a line inside a ``` fence is skipped so documenting the convention does not cite it). Needs full history; treats a shallow clone as a failure rather than passing vacuously. |
| `lint-changelog-tags.sh` | CI gate: a version with a `## [x.y.z]` section in `CHANGELOG.md` must have its `vx.y.z` tag. Closes the one release-ritual gap nothing here could see — `lint-docs.sh` and `lint-proposals.sh` never read that file, and `release.yml` runs only *because* a tag was pushed, so the case it structurally cannot observe is the tag that was never cut (`1.44.1` sat untagged for three weeks; a consumer pinned below it had nothing to advance to, and `git tag --contains` credited its fixes to the next release). The rule is **not** "every heading", because writing the section always precedes pushing the tag and a gate blind to that would redden the merge that RECORDS a release: a heading is due its tag only once its entry was already on `main` when the newest tag was cut. That test ignores file placement and version order, both unreliable here — `1.66.1` sits above `1.67.0`, and a retroactive tag is newest by date while oldest by line. Needs full history; treats a shallow clone as a failure rather than passing vacuously (v1.69.0). |
| `vault-boundary.sh` | Print the boundary a vault declares in its own `CLAUDE.md`. The engine is boundary-agnostic, so anything needing to KNOW a vault's boundary asks the vault here rather than naming a value. Accepts **any** well-formed token, deliberately not a fixed pair — matching a hardcoded set is what made `rag-build`'s cross-boundary skip fail *open* on vaults using a third value. Exit 1 when there is no declaration to find; the caller decides what that means for it. |
| `adopt.d/40-vault-gitignore.sh` | Adoption step: reconcile an existing vault's `.gitignore` with `scaffold/gitignore.tmpl`, **add-only** — appends what the vault is missing (with each entry's explanatory comment), never reorders, removes, or rewrites an entry the vault added itself, and matches on normalized entry text so a different spelling is not duplicated. The template was scaffold-only, so entries added after a vault was created never reached it. |
| `adopt.d/50-normalize-repo-refs.sh` | Adoption step: rewrite a repo page's `ref:` from the full `git describe` form (`vX.Y.Z-<N>-g<sha>`) to its base tag, so the `repo ref is a clean tag` gate lands at **zero** on an already-affected vault. Narrow, reversible, idempotent; `sha:` untouched. Adoption never commits — the rewrite is left for review, as `update.sh` already does for the engine page's provenance. |
| `lint-adopt-paths.sh` | Assert `adopt.d/` steps reference engine assets that exist: no path derived above the engine root (`$ENGINE/..` is the *consumer's* vault), and every literal `$ENGINE/<path>` resolves in the checkout. Catches the class where a step's own bundled asset misresolves, so the step exits 0 and reports as adopted. `--engine DIR` checks another tree. |
| `lint-docs.sh` | Keep the shipped docs honest: every skill documented in this file, every engine-shipped file **`USAGE.md`, `SCHEMA.md` and `README.md`** reference present — written bare (`doctor.sh`) or as a path (`adopt.d/40-vault-gitignore.sh`), since until v1.73.0 the check read this file alone and matched only the bare form, so a reference escaped it by being *more* precise and a reference to the banner-hook adopt step deleted at v1.13.0 sat here through 58 green runs (the gate now rejects that name even in this sentence, which is why it is not written as a path); bounded to the engine's own top-level directories, and skipping tokens carrying `$`, `~` or `*`, so consumer-side and templated paths are not failed closed — no skill or tool stamping a literal `boundary:` value, and **no worktree-taking skill aiming a step at git-ignored per-machine state without naming canonical `$WIKI_PATH`**. That last one is fail-open by nature — a worktree checks out tracked files only, so the step finds an empty directory, reports nothing to do, and exits clean, while the ignored state it meant to touch never appears in a status, a diff, or any other gate. Fifth check (v1.54.3): **every vault walk goes through the shared exclusion** (`vault_pages` / `vault_grep_excludes` in `wiki-root-lib.sh`) rather than a private prune list, and the Python indexer's `SKIP_DIRS` must agree with it — four private copies is how `.worktrees/`, full of other branches' checkouts, went unexcluded in four of five walks. Sixth check (v1.58.0): **every documented hook snippet states a `timeout`** — copy-paste is how a snippet becomes a machine's real wiring, so one missing the field ships the defect to every reader; scoped to the live docs, since `CHANGELOG.md` is history and `proposals/` quote a reporter's observed settings as evidence. Eighth check (v1.74.0): **every skill `description:` fits the host router's cut** — error above 1500 characters, warning above 1400 — because the host truncates the description at ~1536 before routing and the clauses past that point are the `Distinct from` / `NOT for` exclusions; three shipped descriptions were over it, so their exclusions were never applied. |
| `verify-status.sh` | Report the `verified:` correctness signal across repo pages (verified / stale / unverified); `--todo` emits the drainable work-list, `--check` gates. |
| `upkeep.sh` | Drainable maintenance queue (`.upkeep/queue.tsv`): `scan` builds it (stale repo pages + un-verified pages + **repo pages whose clone cannot be located**, reported as `unresolvable:` rather than skipped — the page the tool could not examine is the one most likely to be wrong, and a silent skip made a clean queue mean *"every page whose clone I could find is current"* while reading as *"every page is current"*), `next`/`done` drain it one item per iteration. In-session/human-driven — no `claude` spawn; re-entry sentinel + lock guard any future automated driver. **`sync-clones`** is the opt-in network step: fast-forward-pull the clones backing repo pages, then `scan`. Guarded — a dirty tree, a detached HEAD, a branch with no upstream, a diverged branch and the vault's own checkout are each **skipped and named**, never modified; only a proven fast-forward is applied (no force/stash/rebase, and `git pull` is avoided so `pull.rebase` cannot change what happens). `scan` and `verify-status` stay offline. |
| `crossover.sh` | Deterministic transport for the `crossover` skill: `export`/`import`/`finalize` a batch of pages between vaults with sha256 integrity + a secret-scan; only a hash-matched receipt authorizes the origin soft-delete. `export` splits one block per item by default (`--bundle` for one block, `--block N` to re-emit one); `import` accumulates blocks and names what is still outstanding. |
| `engine-proposal.sh` | Boundary gate + round-trip query for the `engine-proposal` skill: `scan` a drafted handoff block against the consumer vault's own identifiers (slug/dir/git user), home paths, emails, non-generic boundary tags, and secret assignments (fail-closed); `submit` scans then prepares the proposal as a committed file on its own branch and prints exactly what will become public; `push` publishes it. `submit` works in the vault's **pinned `engine/` submodule** — the checkout it defaults to and the only one a consumer vault has — regenerates the derived `PROPOSALS.md` in the same commit so the drift gate does not fail the reporter's own pull request, and restores that checkout to the commit it was pinned at rather than leaving it on a branch cut from `origin/main`; `push` reads the checkout back from the prepared marker, so it needs no `ENGINE_REPO` in the environment. `stash` is **retired** — it wrote a git-ignored per-machine outbox that nothing observed, so *sent* and *never arrived* were indistinguishable; it still runs and warns, and nothing should use it. `status` reports what became of each one — shipped (with the release, and whether your pin has it), merged-not-released, rejected with the reason, partially accepted, open, or unknown — read from the engine checkout's `PROPOSALS.md` + `Proposal:` commit trailers, resolving against `origin/main` rather than the pin. A **bare** `status` lists every proposal this machine holds a local record of — submitted and prepared markers as well as legacy outbox blocks, deduplicated by slug — and an empty result says outright that it is not evidence nothing is outstanding, since a submission from another machine leaves no record here. No `claude`, no network, no node creation. |
| `reflow.sh` · `gen-skills-index.sh` · `gen-projects-index.sh` · `lint-memory.sh` | Soft-wrap normalize · skills-catalog · projects-catalog · memory validation. The two generators target the working tree they are **invoked from** (`bin/wiki-root-lib.sh`): explicit `--wiki`, else cwd's tree when it is a different working tree of the *same repository* as `$WIKI_PATH`, else `$WIKI_PATH` — so running one inside a session worktree updates the index on the branch you are committing from, instead of dirtying the canonical checkout other sessions share. A retarget says so on stderr; `--wiki "$WIKI_PATH"` targets canonical deliberately. Since **v1.66.0 the verdict tools resolve the same way** — `lint.sh`, `lint-links.sh`, `lint-memory.sh`, `verify-status.sh` and `lint-summary-volatility.sh` — because a verdict about a tree the operator is not standing in is worse than no verdict. |
| `new-wiki.sh` | Scaffold a brand-new vault (see README). |
| `link-skills.sh` | Symlink the engine's skills into `~/.claude/skills` so Claude Code discovers them. The bootstrap that makes `/wiki-adopt` available on a fresh machine (idempotent; warn+skips a foreign slot, `--force` to repoint). |
| `skill-sources.sh` | Clone + link a machine's declared **external** skill repos (`~/.claude/skill-sources`, `<git-remote> [dir]` lines); `--check` reports missing (no network). Generic — the machine declares repos; the engine names none. `wiki-adopt` seeds the file; the session banner offers to run this when a declared source is missing (the cold-machine "install my skills" path). |

## Setup & activation

- **New machine (idempotent adoption):** clone the engine standalone, run `bin/link-skills.sh` (so Claude Code can discover the skills), start Claude from any folder, run the **`wiki-adopt`** skill. It detects state and converges: **no vault** → scaffold + wire + seed; **vault already cloned** (a second/Nth machine) → just wire this machine — `bin/wire-machine.sh --wiki DIR --wire-shell --wire-claude-md` (preview with `--check`). Re-run-safe. Single-vault machines only.
- **New vault (scaffolder):** `bin/new-wiki.sh --path … --boundary personal|work --email …` (prompts for anything omitted; auto-provisions RAG unless `--no-rag`; add `--wire-shell --wire-claude-md --create-remote OWNER/NAME` to automate activation), then run `wiki-onboard` to seed it.
- **Turn on semantic recall (existing vault):** `engine/bin/rag-setup.sh && engine/bin/rag-build.sh`. Then just prompt — `wiki-context` recalls automatically.
- **Turn on auto-capture:** add a SessionEnd hook to `~/.claude/settings.json` pointing at `rag-capture.sh` (deterministic — never calls `claude`). Add `RAG_CAPTURE_TRANSCRIPT_PATH=1` to also record the transcript *path* (pointer, not content):

  ```json
  { "hooks": { "SessionEnd": [ { "hooks": [ {
      "type": "command",
      "command": "WIKI_PATH=/path/to/vault RAG_CAPTURE_TRANSCRIPT_PATH=1 /path/to/vault/engine/bin/rag-capture.sh",
      "timeout": 30
  } ] } ] } }
  ```

  **Keep the `timeout`.** The capture cost scales with how many sibling repos the session's
  directory holds — a single repo finishes in well under a second, a workspace root holding
  dozens takes seconds — and the host cancels a SessionEnd hook that outruns its window
  (about one second was observed, with no `timeout` set). The script appends in one block at
  the very end, so a cancellation drops the whole capture, and a dropped capture looks
  exactly like a quiet session: the buffer simply stays empty. Wiring this by tool instead?
  `ensure-hook.sh --timeout 30` writes the same field.

## Keeping it current

`doctor.sh` reports what's behind; `update.sh` applies engine + dep updates in one step (same-MAJOR only — a MAJOR bump needs a reviewed migration). Automatic *checking* runs in CI (Dependabot for actions, a weekly `freshness.yml` cron that opens an issue only on actionable dep/security drift); *applying* to a vault always stays opt-in. RAG deps are pinned in `scaffold/rag-requirements.txt` — bump deliberately, then `rag-setup.sh --force`.

`session-preflight.sh` reports Claude Code + engine staleness at session start and writes a compact cache (`${CLAUDE_CONFIG_DIR:-~/.claude}/.wiki-engine-status`; empty = all current). A hook's *plain* stdout only reaches the assistant's context, so two **user-visible** surfaces read that cache instead — both network-free, and they always agree:

- **Banner** (`session-banner.sh`) — the default. A one-shot `systemMessage` line shown to the user at session start (`wiki-engine <ver> ✓`, or a `⚠` line when stale, plus `⚠ N other session(s) writing — take a worktree` when the lease registry shows live peers). Emitted by `session-boot.sh`, so the single `SessionStart` hook wires it; the peer count comes from `bin/lease-lib.sh`, the same definition `vault-worktree.sh peers` uses.
- **Status line** (`statusline.sh`) — **opt-in**. A persistent bottom row: `dir · model · ctx N%`, plus a color-coded `⚠` when the engine is stale (amber for a normal update, red for MAJOR) and the 5-hour rate limit once it passes 80%. Not auto-wired; enable it yourself with `ensure-statusline.sh` (add-only — sets it only when no status line exists, self-heals the path, never clobbers a status line you configured yourself). **Already have your own row?** Adopt one element instead of the whole line: `statusline.sh --segment ctx` (also `stale`, `rl`, `model`, `dir`; `--segments` lists them) prints just that fragment, nothing at all when it has nothing to say, and keeps receiving threshold/format fixes with the pin — no copied code. The full row is composed from those same segments, so there is one implementation and CI asserts the two cannot drift. Feed each segment the session JSON on stdin; separators and ordering are yours.
  - **The context figure names an action, not just a number**: `ctx 72% — checkpoint soon` (amber) and `ctx 88% — checkpoint now` (red). Compaction is a thing to get *ahead* of — once `checkpoint` has run, the session is disposable and a fresh one starts with the vault as its handoff, so the expensive case is discovering the ceiling mid-task. Read from `context_window.used_percentage`, which Claude Code pre-calculates; truncated rather than rounded, so 84.9% never reads as the higher band. A client that does not send the field, a missing `jq`, or malformed input all degrade to the plain row rather than showing a wrong number.

## Extending the session-start banner (`session-checks.d`)

The SessionStart banner reports engine freshness. A machine can fold in **its own** checks — e.g. a consumer skill repo reporting "first run / catch up" — without the engine knowing anything about them: drop an executable script in `~/.claude/session-checks.d/`. `session-preflight.sh` runs each (deterministic, **must not call `claude`**) and folds the output into the one banner — first stdout line = a compact banner fragment, remaining lines = action/notes for the assistant. Empty output = nothing to report. This keeps the engine generic while letting each layer surface its own state in a single banner.

## Spawning a session (`spawn-session`)

A skill sometimes ends by handing work *elsewhere* — "run that separately, in its own session". Written as advice, accepting it means the operator performs the handoff by hand at exactly the moment the separation was meant to relieve, so the accepted branch quietly collapses into the deferred one. `bin/spawn-session.sh` closes that: the engine knows a session **can** be started, and a drop-in adapter on your machine knows **how**. Same seam as `session-checks.d` above — the engine composes something it does not ship.

```bash
engine/bin/spawn-session.sh --cwd DIR --prompt TEXT [--what LABEL] [--force]
#   exit 0 = started (the handle is on stdout)   exit 3 = not started; by-hand steps printed
```

**The adapter** — executable at `~/.claude/spawn-session` (or wherever `$WIKI_ENGINE_SPAWN_ADAPTER` points). Its whole contract:

| | |
|---|---|
| **argv** | `$1` = working directory, `$2` = the prompt to submit |
| **stdout** | line 1 = a handle the operator can use to find the session (pane id, window name, session id) |
| **exit** | `0` **only once the session is actually running**; non-zero if it could not start |
| **env** | `CLAUDE_SPAWN_DEPTH`, already incremented — pass it through to the child |
| **must** | start the session and **return**; an adapter that runs it in the foreground is killed at `$WIKI_ENGINE_SPAWN_TIMEOUT` (default 20s) |

Nothing richer, deliberately: anything more would put one host's semantics into a boundary-agnostic engine. Drive tmux, a terminal multiplexer, a workspace manager, an IDE — the engine never learns which.

**Every way it can fail lands on the same by-hand fallback, and says which failure it was** — no adapter, not executable, non-zero exit, exit 0 with no handle, or a hang. Reporting a handoff that did not happen is the one fail-open shape that matters here: it converts an accepted decision into a silently lost one, which is strictly worse than never offering to spawn. A machine with no adapter is therefore never worse off than before — it gets the printed steps, which is all it ever had.

**No edge back.** The caller waits only for the adapter to report that it started something. It never polls or reads the spawned session; that session records its own results, which is what makes starting it safe.

**Never wire this to a lifecycle hook.** It starts a session, and a hook whose own trigger the child can re-fire is the fork-bomb structure the engine's `CLAUDE.md` bans — see below. Invoked only on an explicit human accept, and it carries what that rule requires of a deliberate spawn: `CLAUDE_SPAWN_DEPTH` is incremented and refused above a small cap (`$WIKI_ENGINE_SPAWN_MAX_DEPTH`, default 2), and an identical `(cwd, prompt)` spawn inside a short window (`$WIKI_ENGINE_SPAWN_DEDUP_SECONDS`, default 90) is refused so a caller retrying an ambiguous result cannot start the same work twice.

## Boundary & safety (non-negotiable)

- Every vault declares `boundary: personal|work`. **No secrets** (keys, tokens, credentials) in any page. **Content never crosses vaults** — personal↔work is a deliberate manual export. The engine names no value: skills and tools read the vault's declaration (`bin/vault-boundary.sh`), `lint.sh` **errors** on a page whose boundary does not match it, and `lint-docs.sh` fails the build if any shipped skill or tool stamps a literal.
- **NEVER invoke `claude` from a hook or any background/recursive spawn** — that was the `.ai-os` fork bomb. Skills are in-session, on-demand only. The lone exception that may run from a hook is `rag-capture.sh`, precisely because it is deterministic and never calls `claude`.

## Concurrency — more than one session (or agent) writing at once

Two sessions pointed at one `$WIKI_PATH` share **one working tree, one index, and one HEAD**. That is enough to lose work even when they never touch the same file: `git add -A` in either stages the other's in-progress edits, and `git reset`/`checkout` moves the other's HEAD. Simultaneous edits to one file are last-writer-wins **on disk, before git is involved at all**, so no commit-time lock can help.

`bin/vault-worktree.sh` layers four defences, each covering what the one below cannot:

| Layer | Command | What it prevents |
| --- | --- | --- |
| **Isolation** | `ensure` | The filesystem race. Each session gets its own worktree (own dir + own HEAD, shared `.git`) on a `wt/<session>` branch. ~0.4 s, <1 MB. It reports a base that omits work — whether the branch it reattached to is behind `origin/main`, or canonical `main` holds unpushed commits the fresh cut lacks. The second one is quiet by nature: a search for the missing work exits 0 with no output, which reads as "nobody wrote this yet", so the session duplicates it instead of conflicting with it. |
| **Enforcement** | `guard` | Isolation being skipped. Refuses a commit made in the canonical checkout, so the unsafe path can't be taken out of habit. Wired from the vault's `pre-commit`. It judges the **staged set**, not the tree: a commit staging only submodule pointers (gitlinks) is allowed, because `git worktree add` never populates a submodule, so advancing the engine pin is the one commit no worktree can make. Stage anything beside it — which `commit -am` does in a shared tree — and the refusal stands. Before that, the documented pin bump was refused outright and its workaround was `WIKI_WORKTREE=0`, i.e. turning isolation off for the whole command to land one legitimate commit. When it refuses, it also names how to **carry the staged work** into the worktree it is sending you to — a `git stash push -- <your paths>` listing your actual staged paths, popped in the worktree. `ensure` cuts a fresh branch and carries nothing, and the reflex `git diff > patch` reports *unstaged* changes only, so against a fully-staged tree it writes an empty file and the discard that follows takes the only copy. |
| **Visibility** | `lease` / `peers` | Surprise. A session declares the paths it intends to write; `peers` lists live sessions. **Advisory** — git decides real conflicts at merge, and refusing overlap would block the common harmless case of two sessions touching one index file. The job is to make a collision course visible while re-planning is still cheap. Liveness is structural first, clock second: a session whose worktree *and* branch are both gone has provably finished and drops out immediately, so `peers` never accumulates ghosts; one that merely stopped refreshing is reaped on `WIKI_LEASE_STALE_MIN`. |
| **Visibility (project)** | `claim` / `peers` | Two sessions converging on the same *project* without either being able to see it. `claim <slug>` records the project on this session's lease (one record, one liveness rule — a second presence store would give a second answer to the same question) and names any live peer on that slug with its activity age; `wiki-context` does it for the project it loads. **Advisory, deliberately not a lock.** Vault edits already collide as merge conflicts and working trees are already isolated; what has *no* coordination surface is the work outside version control — investigation both sessions repeat, and commands issued against external systems, where they contend silently. A claim whose session died reports `STALE` rather than being deleted, so a session that ended mid-work stays visible. |
| **Serialization** | `integrate` | HEAD races at the one genuinely shared step. Rebases your branch onto `main` **inside your worktree** (so a conflict lands in your tree, not in canonical mid-merge), then fast-forwards `main` under an atomic lock. |

The session-start banner reports live peers, because the guard only fires at *commit* time — by then the editing has already happened somewhere.

Exit codes from `integrate`, so a loop or agent can branch on them: **1** dirty worktree, **2** not in a worktree, **3** rebase conflict (resolve in your worktree, re-run), **4** lock wait timed out.

Single-session machine, or a deliberate direct-to-main flow: `WIKI_WORKTREE=0` turns isolation and the guard off together.

## Gate seam (`$WIKI/.wiki-gates.conf`)

Optional, `key = value`, **parsed and never sourced** — a config file that can execute code is a config file that can own the machine running the gate. Absent means engine defaults. The engine composes the seam; the vault supplies the values, so no consumer's strings live in the engine.

| Key | Default | What it names |
| --- | --- | --- |
| `external_refs` | `.wiki-gates-external-refs` | A file of link targets that must **never** resolve in this vault — another boundary's pages, engine files, skill names. Listed targets are silent instead of warning as stubs, so a permanent cross-boundary reference is not mistaken for rot a future session should "fix". |
| `summary_volatility_markers` | *(engine's `scaffold/summary-volatility-markers.txt`)* | A file of EREs that mark a project `summary:` as naming **state** rather than identity. Overridable per-vault because which words are volatile is a property of how a given vault writes, not of the engine — so tuning the list must not require an engine release. A vault file **replaces** the engine default wholesale. |
| `summary_baseline` | `.wiki-gates-summary-baseline` | The grandfathered-summaries ratchet, seeded once at adoption. **Keep it tracked** (unlike `foreign_boundary_patterns`): it holds no sensitive strings, only `<slug>\t<sha256(summary)>` pairs, and every machine and CI must agree on the same baseline or the gate means something different in each place. Keying on the summary's hash rather than its slug is what makes the ratchet one-way — rewriting a summary drops its exemption automatically, so the file can only shrink without a deliberate re-seed. |
| `foreign_boundary_patterns` | `.wiki-gates.local` | A file of EREs this vault's pages must not match — the foreign-boundary denylist. **Keep it git-ignored:** naming the forbidden strings in a tracked file commits the other boundary's identifiers into this vault's permanent history, which is the thing the gate exists to prevent. The trade-off is that a fresh clone starts unarmed, so an unarmed gate reports `not armed` rather than passing silently. Matches print the file, line, and the *pattern* — never the matched text, which would put the foreign string in CI logs. |

## Config knobs (environment)

- `WIKI_PATH` — the vault root the skills/tools resolve from.
- `UPKEEP_STALE_ACTIVE_DAYS` / `UPKEEP_STALE_PAUSED_DAYS` — how long an untouched project page may go before `upkeep scan` queues it (defaults 14 and 90). Knobs rather than constants because "how often should an active project move?" is a property of the consumer's cadence, not of the engine. `paused` gets its own longer horizon because it asks a different question — *should this still be paused?* — not *is this current?*
- Embedding: `RAG_LOCAL_MODEL`, `RAG_PIP_PKG`, `RAG_REQUIREMENTS`, `RAG_MODEL_CACHE` (where weights live; default `${XDG_CACHE_HOME:-~/.cache}/wiki-engine/models`, machine-global — set it to `$WIKI/.rag/models` for vault-local); or an endpoint via `RAG_EMBED_API` (`ollama`|`openai`) + `RAG_EMBED_URL` / `RAG_API_KEY`.
- Recall: `RAG_RAW_WEIGHT` (curated-over-raw penalty, default `0.80`).
- Capture: `RAG_CAPTURE_TRANSCRIPT_PATH`, `RAG_CAPTURE_FILES`, `RAG_CAPTURE_COMMITS`, `RAG_CAPTURE_SINCE`, `RAG_CAPTURE_STDIN_TIMEOUT` (seconds to wait for hook JSON on stdin, default `2`; a timeout means "no payload" and falls back to `--repo`/`$PWD`, so a caller whose stdin is an open pipe nobody closes gets an answer instead of a hang).
