HANDOFF — engine defect report slug: worktree-staleness-warning-omits-the-behind-case boundary: generic (engine-domain; contains no consumer-private context)

Title: `vault-worktree.sh ensure`'s staleness warning prints `rebase <main>` as its remedy while measuring only whether canonical `<main>` is AHEAD — so when `<main>` is also BEHIND `origin/<main>`, following the printed command detaches the session branch from `origin/<main>` and neither push nor `integrate` can recover it

Engine version: v1.73.4 — the tag this vault is pinned to.

Still live at that pin: the mechanism was re-confirmed 2026-09-03 by reading `bin/vault-worktree.sh` at the pinned commit — `warn_if_local_main_ahead` (lines 205-218) computes exactly one count and prints its remedy unconditionally, and `integrate`'s divergence branch (lines 648-675) still exits 3 with the same message. `git diff v1.73.3..<pin>` touched only `CHANGELOG.md`, `PROPOSALS.md`, `proposals/` and `scaffold/rag-requirements.txt`, so the script is byte-identical to the version the failure was observed on. **Scope of that confirmation, stated because it is narrower than a reproduction:** the failure itself was observed live on 2026-09-02; today's check re-read the code path rather than re-staging the divergence, so this is "the code that failed is unchanged", not "it failed again today". A deterministic fixture reproduction is given below and has not been run.

Observed:

1. `behind_count()` (line 187) is `git -C "$WIKI" rev-list --count "$1..$2"` — a one-directional count.
2. `warn_if_local_main_ahead "$wt" "$branch" "$base"` (line 205, called from the `ensure` paths at lines 299, 367 and 373) resolves `mainref` from canonical `HEAD`, returns early if `mainref` equals the base, then computes `n="$(behind_count "$branch" "$mainref")"` — the commits canonical `<main>` holds that the freshly cut branch does not. For `n > 0` it prints three lines, the last being: `Rebase before surveying or writing:  git -C <worktree> rebase <main>`.
3. **The function computes no second count.** Nothing in it, or reachable from it, evaluates `rev-list --count <main>..origin/<main>` — whether canonical `<main>` is also *behind* the remote. The warning therefore fires identically in two states it cannot distinguish: `<main>` ahead only, and `<main>` ahead **and** behind. Control that this is a real absence and not a missed line: `grep -n 'rev-list' bin/vault-worktree.sh` returns one hit, line 187, inside `behind_count` itself — so there is exactly one counting primitive in the file and the function calls it once, with the branch and canonical `<main>` as its two arguments.
4. In the ahead-only state the printed command is correct and harmless: canonical `<main>` already contains `origin/<main>`, so rebasing the branch onto it leaves the branch a descendant of `origin/<main>`.
5. In the ahead-and-behind state the printed command is wrong. Observed live 2026-09-02 on a vault where canonical `<main>` was 1 commit ahead (another session's unpushed commit) and 1 behind (merges landed on the remote since): the branch, cut off `origin/<main>`, was rebased onto `<main>` as instructed and stopped being a descendant of `origin/<main>`. A push was rejected as non-fast-forward, and `integrate` could not resolve it — `integrate` reconciles canonical and then fast-forwards `<main>` **to** the branch, so a branch whose history no longer contains `origin/<main>` is outside what it can fix. `integrate` reports this as `<main> has DIVERGED from origin/<main> — nothing was integrated` and exits 3 (lines 672-674).
6. **The engine already holds the correct remedy, in this same file, on a surface an operator sees.** `integrate`'s refusal prints it at line 673: `reconcile canonical first (e.g. rebase <main> onto origin/<main>), then re-run integrate` — the local ref moving, which is exactly what `ensure` should have said and did not. The principle behind it is stated in the comment at lines 637-639: *"Rebasing onto origin/<main> instead is NOT the fix, though it looks like the obvious one-word change: the fast-forward below then refuses, because local <main> is no longer an ancestor of the rebased branch. The local ref has to actually move."* So this is not missing knowledge and not even missing wording — the right sentence already exists in the file, on the surface reached only AFTER the operator is already stuck. Two surfaces of one script give opposite advice about the same divergence, and the one that speaks first is the wrong one.
7. The warning's own text is otherwise accurate and worth keeping: it correctly explains that the worktree cannot see never-pushed work and that a search for it exits 0, which reads as "never written". The defect is confined to the remedy line and to the missing second measurement.

Expected:

`ensure` should read both counts before printing a remedy, and print a remedy that is correct for the state it measured:
- ahead only → the current line (`git -C <worktree> rebase <main>`) is correct; keep it.
- ahead **and** behind → the remedy is to move the local ref first, not the branch, and the warning should say so and say which two commands do it.

The stronger form of the same Expected, which intake may prefer: print a remedy that is safe in **both** states unconditionally, so the warning does not depend on getting the classification right. Either satisfies the requirement that following the printed command never produces a branch that is not a descendant of `origin/<main>`.

Checked against the suggested fix below, because they are separate fields and nothing in this block forces the comparison: the fix adds the second `rev-list --count` and branches the printed text on it, which produces the first form of the Expected directly. It does **not** produce the second form — a single unconditional remedy — so if intake prefers that, the fix below is the wrong shape and the Expected is the half to keep. Stated rather than left for intake to notice.

Reproduction (generic, deterministic — NOT RUN; the live observation is item 5 above):

  1. In a scratch vault clone, with `<main>` and `origin/<main>` equal, cut a session worktree: `WIKI_PATH=<vault> WIKI_WT_SESSION=<slug> <vault>/engine/bin/vault-worktree.sh ensure`. Note the branch is cut off `origin/<main>`.
  2. Make canonical `<main>` **behind**: land a commit on the remote `<main>` by any route, then `git -C <vault> fetch origin <main>` without merging it.
  3. Make canonical `<main>` **ahead**: commit once directly on canonical `<main>` and do not push it.
  4. Re-run `ensure` for the same session slug. -> It prints `<main> holds 1 commit(s) origin/<main> lacks — committed locally, never pushed.` and `Rebase before surveying or writing:  git -C <worktree> rebase <main>`. It prints nothing about being behind.
  5. Run exactly that command in the worktree, then `git -C <worktree> push -u origin <branch>`. -> The push is rejected as non-fast-forward. `git -C <vault> merge-base --is-ancestor origin/<main> <branch>` now returns non-zero — the control that separates this from an ordinary stale branch.
  6. Run `vault-worktree.sh integrate`. -> `<main> has DIVERGED from origin/<main> — nothing was integrated`, exit 3.

  Both counts, for a reader confirming the state before acting: `git rev-list --count origin/<main>..<main>` (ahead) and `git rev-list --count <main>..origin/<main>` (behind).

Failure shape: **fail-open.** The warning fires, prints a remedy that looks correct and is correct in the more common of the two states, and nothing measures or reports the condition that makes it wrong. The operator follows documented advice and lands in the one state `integrate` declines to resolve, at which point the tool that caused it is several steps behind them. It is not data-loss: the work is committed on the session branch and recoverable by hand. But the obvious recovery is dangerous in a way worth flagging — `reset --hard origin/<main>`, which the engine's own squash-merge divergence path uses safely (the reset at lines 665-667), is gated there on the two trees being byte-identical and canonical being clean (lines 659-660). In this state the trees genuinely differ, because canonical's extra commit is real unpublished work, so the same reset destroys it. `integrate` already draws that distinction in code; an operator reading only the printed advice does not have it.

Already ruled out:

- **That this is the same defect as `integrate`'s squash-merge divergence.** It is not. That case is content-equal with republished history and `integrate` adopts it automatically (gate at lines 659-660, reset at 665, message at 667). Here the content differs, so `integrate` correctly refuses — the refusal is right, and the defect is upstream of it, in the advice that produced the state.
- **That the warning is wrong to fire.** It is not; the ahead case is real and the explanation it prints about invisible unpushed work is accurate and should survive any fix.
- **That `integrate` could be changed to absorb this instead.** `integrate` fast-forwards `<main>` to the branch, and a branch not descended from `origin/<main>` cannot be the target of that fast-forward without discarding remote history. Fixing it there means picking a side silently, which is the behaviour the comment at lines 669-671 and the refusal at 672-674 exist to prevent.
- **That the remedy is only wrong when the counts are 1 and 1.** The 1-and-1 case is what was observed; the mechanism depends only on both counts being non-zero, not on their size. Not verified at larger counts.
- **That a fetch would have surfaced it.** `ensure` warns about local-only commits precisely because no fetch can see them; the missing measurement is a local `rev-list`, not a network call.

Suggested fix (HOLD LOOSELY — may be wrong):

- (a) In `warn_if_local_main_ahead`, compute the second count — `behind_count "$mainref" "$base"` — and branch the printed remedy on it. Both counts already come from the existing primitive; no new machinery.
- (b) When behind is zero, print today's line unchanged.
- (c) When behind is non-zero, say that canonical is divergent, and print the two commands that move the local ref: `git -C <vault> rebase origin/<main> <main>` then re-base the session branch on the result. Name the reason in one clause — the branch must stay a descendant of `origin/<main>` or nothing can integrate it — because the operator is about to run it in a state where the wrong command is one word away.
- (d) Consider whether `ensure` should refuse to hand back a worktree at all while canonical is divergent, rather than warn. That is a fail-closed change to a default and needs the design pass; it is raised, not proposed. Note the argument against it: `ensure` is the first thing a session runs, and a refusal there blocks work on a condition the session did not create.
- (e) Whatever shape is chosen, the case that must be tested is ahead-and-behind, and the near-miss that must also be tested is ahead-only — a fix keyed on "canonical is not equal to origin" flags the harmless case too and would print the heavier remedy on every ordinary commit-now-push-later session, which is how a correct warning becomes one nobody reads.
