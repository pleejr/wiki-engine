HANDOFF — engine improvement proposal slug: memory-note-lifecycle-fields boundary: generic (engine-domain; contains no consumer-private context)

Title: `status: superseded` is the one memory-note field value the engine's own lint acts on and `SCHEMA.md` documents nowhere; there is no field for what superseded a note, so supersession happens in prose and no script can follow it

Engine version: v1.73.4 — the tag this vault is pinned to. Engine line references and the consumer measurements below were taken on 2026-09-03. The pin is one commit behind the engine's `origin/main`, not equal to it.

Problem (generic — three findings on one seam, each with its own control):

1. **The engine acts on a value it never defines.** `bin/lint-memory.sh` line 141 reads a note's `status:` and exempts `status: superseded` from the index-catalog-drift warning; its header states this at line 13. That is the whole vocabulary — one value, honoured in one place. `SCHEMA.md` defines `status:` values only for **project** pages (line 61: `planned|active|paused|done`) and names `status` as a scanned **skill** frontmatter key (line 65). It says nothing about a memory note's `status:` at all: not `current`, not `superseded`, not that the field exists. Control, so this is not a search that missed a section: `grep -n status SCHEMA.md` returns eight lines, all about project pages, repo provenance, skills, or the generated Projects buckets — the memory node's own `status:` appears in none of them. So the only way to learn the value that changes lint behaviour is to read the lint.

2. **There is no field naming the successor, so a superseded note is a dead end for a script.** `lint-memory.sh` requires `title`, `type`, `boundary` as ERRORs (line 106), warns on a missing `updated` (line 109), validates `type` against `memory | lesson | decision | preference` (line 33), and requires ≥2 outbound wikilinks (line 128). Nothing requires, validates, or reads a `superseded_by:` — the field does not exist in the engine. Measured on one consumer vault, 2026-09-03: 404 memory notes, of which **47 carry `status: superseded`** and **0 carry `superseded_by:` or `supersedes:`**. Control that this is a real absence and not a broken probe: the same grep pattern finds `status: superseded` in 47 files, so the pattern and the population are both live; the successor fields are genuinely absent, not merely unmatched. The consequence is that a reader who lands on a superseded note has to find its replacement by reading prose — and the `≥2 wikilinks` rule guarantees there ARE links, which makes it worse, because none of them is marked as *the* successor. A tool cannot distinguish the pointer from the related-reading.
   - Second-order effect worth stating because it is the one that bites: the index-drift exemption at line 141 means a superseded note is allowed to vanish from `index.md`. Combined with no successor field, a superseded note becomes unreachable from the map AND silent about where to go instead — reachable only by the inbound wikilinks of whatever still points at it. That is a fail-open shape: nothing reports it, and the note reads as intact.

3. **`created:` is written by convention and enforced by nothing, while `updated:` is warn-only.** The engine's own `skill-candidates` bar is dated evidence — its whole method is reading `created:` and `updated:` to decide whether a procedure has repeated over weeks — yet `created:` is in neither the ERROR list nor the WARN list of the lint that validates every note. A note missing `created:` passes clean and is invisible to the recurrence query that depends on it. That is not a hypothetical ordering: the field is load-bearing for one engine skill and unchecked by the engine's only note lint.

Motivating use case (generic): a vault corrects a note — the rule changes, or two notes merge into one. The engine's stated practice is supersession (the lint header says memory is "kept current by supersession + this lint"). The operator wants the retired note to say, in a field, what replaced it, so a reader arriving from an old link is forwarded rather than left reading a rule that is no longer true; and wants the one status value the engine reacts to to be documented where every other node's fields are.

Proposed shape:

- (a) **Document the memory-node `status:` vocabulary in `SCHEMA.md`**, beside the project-page `status:` line, as `status: current|superseded` — the two values in use — and state the behaviour that attaches to `superseded` (exempt from index-drift, per `lint-memory.sh` line 141). One sentence. This is the item with no design question in it; do it first, independently of the rest.
- (b) **Add `superseded_by:` as an optional single-slug field**, and make `lint-memory.sh` enforce the pairing in both directions: ERROR if `status: superseded` and no `superseded_by:`; ERROR if `superseded_by:` names a slug that does not resolve to a page in the vault (a forwarding pointer to nothing is worse than none — it reads as a resolved redirect); WARN if `superseded_by:` is present while `status:` is not `superseded`. **Single slug, not a list**, and this is the design decision: a note superseded by three notes has no unambiguous forward target, so a list would let the field be written and still not answer the question it exists to answer. If a merge genuinely fans out, the vault's answer is a hub page — the thing that already exists in the node model — and `superseded_by:` points at the hub.
- (c) **Do NOT add `supersedes:`.** It is derivable — the inverse of every `superseded_by:` in the vault — and a hand-maintained inverse index drifts, which is the failure this engine has already named and fixed for proposal status (`engine-proposal.sh status` exists precisely because a hand-kept `status:` line drifted). If the reverse view is wanted, generate it.
- (d) **Promote `created:` to a checked field** — WARN on missing, matching how `updated:` is handled today rather than inventing a third severity. Not an ERROR: existing vaults have notes without it, and an ERROR would fail a commit on unrelated content, which teaches `--no-verify`. Say in the `SCHEMA.md` sentence why it is checked at all: it is the field `skill-candidates` reads to decide recurrence, so a note without it is invisible to that pass.
- (e) **Migration is a consumer's job, not the engine's.** Ship (b) as an ERROR only for notes that declare `status: superseded`, so a vault with 47 such notes fails until it fills them in — that is the correct blast radius, because those 47 are exactly the notes whose successor is unrecorded, and the fix is one field each. Say so in the CHANGELOG entry: an arriving vault should expect N failures where N is its count of superseded notes.

Alternatives considered:

- **Keep supersession in prose (an inline "Correction"/"RETRACTED" block) and document THAT as the mechanism.** This is the honest alternative and it should be considered on its merits, not dismissed — it needs no schema change and it puts the correction where a reader is already looking. Rejected because it is unreadable by any script: nothing can list the vault's retired notes, nothing can forward a stale link, and the index-drift exemption already lets those notes leave the map. A convention with no machine-readable surface cannot be checked, and the engine's position everywhere else (derived catalogs, provenance stamps, proposal outcomes) is that lifecycle state belongs in frontmatter.
- **Make `superseded_by:` a list.** Rejected under (b) — the field's only job is to forward a reader, and a list of three does not.
- **Reuse `updated:` as the supersession signal.** Rejected: `updated:` moves on every edit, so it cannot distinguish a retired note from a maintained one, and `lint-memory.sh` already treats it as an edit stamp.
- **Have the lint auto-insert `superseded_by:` from the note's first wikilink.** Rejected: the `≥2 wikilinks` rule means every note has links, and the first one is related-reading as often as it is a successor. A guessed forward pointer is a wrong answer that looks authoritative.
- **Make `created:` an ERROR.** Rejected under (d): a gate that is red on arrival on content unrelated to the commit is the failure the engine has already fixed twice in `vault-worktree.sh`.

Acceptance criteria:

- `SCHEMA.md` states the memory-node `status:` vocabulary and the `superseded` behaviour. Control: today `grep -n status SCHEMA.md` returns no line about a memory note, so the absence is verifiable before and the presence after.
- `lint-memory.sh` errors on a note with `status: superseded` and no `superseded_by:`. Red before green, on the subject not the assertion: take a conforming fixture note, delete only its `superseded_by:` line, run the lint, require a non-zero exit whose message names that file and that field; restore, require green.
- Near-miss, which is the run that actually matters here: a note with `superseded_by: <slug-that-does-not-exist>` must ALSO error. A check that only tests for the field's presence passes this input while forwarding readers to nothing — and presence-only is the natural implementation, so this is the coincidence the first test cannot catch.
- Second near-miss: a note with `status: current` and no `superseded_by:` must pass, and a note with `status: current` **and** a `superseded_by:` must warn. A rule keyed on the field alone rather than on the pair gets the first of these wrong.
- `created:` missing produces exactly one WARN and does not change the exit code, matching `updated:`'s existing severity. Control: a note missing both produces two warnings, not one — otherwise the second check is not running.
- No `supersedes:` field is added anywhere.
- The CHANGELOG entry states the expected failure count shape for an upgrading vault.
- `bin/lint-memory.sh` names no consumer's strings (the engine's own rule at `bin/lint.sh` line 32).

Redactions: no note title, slug, body text or correction is reproduced. The consumer figures are aggregates only — 404 memory notes, 47 with `status: superseded`, 356 with `status: current`, 0 with `superseded_by:` or `supersedes:` — from one vault on one date. The one note accounted for by neither status value is reported as measured rather than explained; its status was not read. Nothing was omitted for being awkward to scrub.

Instruction to engine-dev: (a) is a one-sentence doc fix with no design question — ship it whether or not the rest survives review. (b) changes a frontmatter contract and adds a fail-closed ERROR to a script that runs as a write-time gate, so it earns the full design pass AND the diff-review gate; the questions to settle there are the single-slug decision and whether the resolve-check should follow `lint-links.sh`'s external-refs seam (a slug declared external should presumably not satisfy a `superseded_by:`, since forwarding a reader to a page the vault does not contain is the failure the check exists to prevent — decide it, do not inherit it). Re-measure the 47/0 counts on your own vault before sizing the migration note. Create the project under this slug.
