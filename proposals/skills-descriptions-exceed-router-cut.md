HANDOFF — engine defect report slug: skills-descriptions-exceed-router-cut boundary: generic (engine-domain; contains no consumer-private context)

Title: Three skill descriptions exceed the host router's ~1536-character cut, so their `Distinct from` / `NOT for` clauses are never seen at routing time

Engine version: v1.73.4 — the tag this vault is pinned to. Still live at that pin: re-measured 2026-09-03 with awk `length()` on the `description:` value (the `description: ` prefix stripped) of every `skills/*/SKILL.md` at the pinned commit. `engine-proposal` 2446, `skill-candidates` 1982, `prove-the-test-can-fail` 1845 — identical to the first measurement on 2026-09-01; the other nine are under the cut (largest `crossover` 1035, then `drain` 863, `verify` 814). The pin moved v1.73.3 -> v1.73.4 in between and touched no `skills/` file, which is why the numbers are unchanged. The pin is one commit behind the engine's `origin/main`, not equal to it.

Observed: Claude Code presents each skill's description to its routing step truncated at roughly 1536 characters. Offsets of the disambiguation clauses **inside the description value**, i.e. with the 13-character `description: ` prefix stripped — state the frame, because measuring the raw line instead shifts every offset by exactly 13 and the two sets of numbers look like a disagreement:

  engine-proposal          len 2446   `Triggers:` @1193   `Distinct from` @1864   `NOT for` @2322
  skill-candidates         len 1982   (no `Triggers:` label)  `Distinct from` @1601   `NOT for` @1845
  prove-the-test-can-fail  len 1845   (no `Triggers:` label)  `Distinct from` @938    `NOT for` @1567

So for `engine-proposal` and `skill-candidates` every exclusion clause is past the cut; for `prove-the-test-can-fail` the `NOT for` clause is. `engine-proposal` spends ~730 chars on 20 trigger phrases before its first `Distinct from`; `skill-candidates` spends ~900 chars on design rationale ("since its own ranking axes cannot see whether a skill is the right form at all") before naming a single trigger. Nothing in the engine measures description length: `bin/gen-skills-index.sh` reads `description:` only to render it (line 54), and `bin/lint-docs.sh` does not read it.

Expected: every description keeps what/when, `Triggers:`, `Distinct from` and `NOT for` inside the first ~1400 characters, and a deterministic check fails when a description crosses the budget — the same way `gen-skills-index.sh --check` fails on catalog drift. The description is the routing surface; a clause the router cannot see is not a rule.

Reproduction (generic):
  1. cd <engine checkout>
  2. for s in skills/*/SKILL.md; do printf '%s ' "$s"; awk '/^description:/{sub(/^description: */,""); print length($0)}' "$s"; done | sort -k2 -n
  3. For each result above 1536, `awk '/^description:/{sub(/^description: */,""); print index($0,"NOT for")}'` on the same file — the `sub` matters: without it every offset reads 13 higher than the numbers above. -> three files above 1536; each has its `NOT for` offset above 1536.

Failure shape: fail-open — the skill still routes on its positive triggers; the exclusions silently stop applying. The visible symptom is a skill firing on a case its own description assigns to a sibling (`crossover`, `checkpoint`, `drain`), with nothing to say why.

Already ruled out:
  - A display artefact of one terminal width: the truncation is in the text the router receives, not in rendering.
  - The trailing clauses being redundant: in all three the `Distinct from` names a sibling engine skill that shares trigger vocabulary, so the clause is the only thing separating them.

Suggested fix (HOLD LOOSELY — may be wrong): (a) Replace the three descriptions with the drafts below (1362 / 1347 / 1285 characters, measured). Each keeps what/when, the commands that matter, an explicit `Triggers:` line, `Distinct from`, and `NOT for`, and moves rationale to the body. (b) Add a description-length check to `bin/lint-docs.sh` or `gen-skills-index.sh --check`: fail above 1500, warn above 1400, so the cut cannot be re-crossed silently. (c) Trigger phrases dropped from `engine-proposal` ("here is a HANDOFF block", "the engine is broken here", "what happened to the proposal I sent", "is that engine proposal still open") are a judgement call; the engine has no trigger-eval set to score them against.

  Drafted `engine-proposal` description (1362):
  Hand a wiki-engine improvement or DEFECT from a consumer vault upstream to the engine-dev queue, and intake it on the other end. Consumer side: genericize and boundary-scrub the idea (strip vault/org/repo names, users, emails, paths, secrets), run the fail-closed `engine-proposal.sh scan`, then `submit` + `push` it as a file in the engine's `proposals/` queue by pull request — never a local edit inside `engine/`, which the next update discards, and never a node in the consumer vault. A defect block separates Observed from Suggested fix, names the failure shape (fail-closed / fail-open / data-loss), and confirms the bug is live at the pinned tag. Engine-dev side: reproduce first, design-review the arrival, record outcome + reason in the proposal frontmatter, cite `Proposal: <slug>` on the fix. `status` answers "did it ship". Triggers: "engine-proposal", "propose this upstream", "this should live in the engine", "I found a bug in the engine", "report this defect upstream", "should I fix this in engine/", "intake this proposal", "did my proposal ship", "check my outbox against the engine". Distinct from `crossover` (MOVES an existing page between vaults with integrity + soft-delete) — this originates a forward-only idea that never was a node; distinct from `checkpoint` (curates INTO this vault). NOT for recording a decision or lesson here.

  Drafted `skill-candidates` description (1347):
  Mine the vault's durable record — `memory/` notes, `log.md`, the session buffer — for procedures repeated often enough to deserve a skill, and report ranked CANDIDATES with dated evidence. A candidate needs 3+ dated occurrences spread over weeks with stable steps and a varying subject, never the session that just ended. Reports name, procedure, evidencing notes, and an overlap check against the installed catalog, then puts EVERY candidate to the operator as a develop / discard / defer choice — it recommends, never decides — and records those verdicts itself as `type: decision` notes tagged `skill-candidate`, in its own worktree and commit. First run on an un-mined vault is a backlog drain (expect many); later runs sweep forward from the newest verdict (expect zero or one). Never writes a `SKILL.md` and invokes nothing. Triggers: "mine the vault for skill candidates", "should this be a skill", "what should I turn into a skill", "have I done this enough times to encode it", "find the skills hiding in my notes", "catch up on the skills I never wrote", or when `checkpoint` offers it. Distinct from `checkpoint` (distills facts INTO `memory/`; offers this pass, never runs it) — this reads those notes back out. NOT for writing or debugging a skill, and NOT for a one-off procedure — one session is a feeling, not evidence.

  Drafted `prove-the-test-can-fail` description (1285):
  Prove a check, gate, lint rule, CI step or test actually FAILS when what it watches is broken — by running it, not reading it. Breaks the SUBJECT (never the assertion), requires a real red whose message names the right thing, restores by explicit path, requires green again, then feeds a NEAR-MISS that merely resembles the subject and requires rejection, since a check can go red on an obvious break and still pass a coincidence. Reports both runs' actual output as evidence. Refuses on a dirty working tree — it cannot tell its own mutation from uncommitted work, and restore would clobber it. Triggers: "prove this test can fail", "did this go red first", "red before green", "is this gate actually checking anything", "make sure this check works", "this check has never failed", "verify the fixture took", or right after writing any new gate or assertion. Distinct from `drain` (carries red-before-green as one clause of the release loop), from read-only artifact review (e.g. a `scrutinize` skill, which never executes), and from auditing a verdict that already came back — the axis is whether a verdict exists: none yet and the check has never failed → this skill. NOT for debugging a check already failing, NOT for doubting a pass that exists, NOT for writing the check.
