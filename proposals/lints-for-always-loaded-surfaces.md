HANDOFF — engine improvement proposal slug: lints-for-always-loaded-surfaces boundary: generic (engine-domain; contains no consumer-private context)

Title: The engine lints every derived and per-page surface but leaves the two ALWAYS-LOADED ones — `index.md` hooks and the vault `CLAUDE.md` preferences section — unmeasured, so the one rule they both state about themselves is the one rule nothing enforces

Engine version: v1.73.4 — the tag this vault is pinned to. All engine line references and the consumer measurements below were taken on 2026-09-03. The pin is one commit behind the engine's `origin/main`, not equal to it.

Problem (generic — true for any consumer vault):

1. **What the engine already lints, and the shape of the gap.** `bin/lint.sh` composes checks over derived catalogs (`gen-skills-index.sh --check`, `gen-projects-index.sh --check`), per-page frontmatter (`lint-memory.sh`, boundary presence and match, repo provenance), page-level prose (`reflow.sh --check` soft-wrap), link integrity (`lint-links.sh`), and one *length-adjacent* rule: `bin/lint-summary-volatility.sh`, which polices a project page's `summary:` because that field is rendered into `index.md`. So the engine already accepts the premise that a field which lands on the map deserves a mechanical check. The two surfaces that are loaded on **every turn of every session** — the `index.md` memory hooks, and the vault `CLAUDE.md` preferences section — have no check of any kind.

2. **Both surfaces state a rule about themselves in prose, and prose is not a gate.** `SCHEMA.md` line 62 already carries the analogous rule for a project summary ("**`summary:` names IDENTITY, not state**"), and `bin/lint-summary-volatility.sh` line-for-line enforces it as a marker heuristic. There is no equivalent statement in `SCHEMA.md` for what an `index.md` hook is, and no check. A vault that writes the rule into its own `CLAUDE.md` or under its own `## Memory` header has written a rule the engine cannot see and the next session re-decides.

3. **The failure is silent and cumulative, which is why it needs a gate rather than a reminder.** A hook is written at the moment its note is written, by a session that has the note's evidence in hand — so inlining a date, an occurrence count, or a "second instance" narrative is the locally natural thing to do, and no single instance looks wrong. The cost is paid on every subsequent turn of every subsequent session, by a reader who cannot see the accumulation. Measured on one consumer vault, 2026-09-03: 567 hook lines in `index.md`, mean 32.4 words, **361 of 567 over 25 words**; 31 hook lines inline a `YYYY-MM-DD` date. Longest single hook: 164 words. The same vault's `CLAUDE.md` carries an explicitly frozen word budget for its preferences section and a hand-written re-measurement history proving the budget was checked three times by hand — which is exactly the work a lint does for free, and the fact that it was done by hand three times is the evidence that it is a recurring cost, not a one-off cleanup.

4. **The two existing hand-run controls do not compose.** `lint-summary-volatility.sh` skips `done` pages, on the stated reasoning that a done page's claims are frozen; but a `summary:` is identity, which is frozen regardless of status, so its own SCHEMA rule (line 62) argues the skip is wrong. And the volatility check has no word cap at all — a 54-word summary passes as long as it carries no state marker. So even the one length-adjacent lint the engine has does not measure length.

Motivating use case (generic): a consumer vault runs a session; the map and the preferences file are in context before the first tool call. The operator wants the always-loaded budget to be a number a script reports, not a paragraph a session has to remember and re-measure by hand, and wants a hook that inlines its own evidence to be caught at commit time rather than at the next audit.

Proposed shape:

- (a) **`bin/lint-index-hooks.sh`** — over the vault's `index.md`, for every hook line matching `- [[<slug>]] — <text>`: **warn** above `INDEX_HOOK_WARN_WORDS` (default 25) and **warn** on an inlined `20[0-9]{2}-[0-9]{2}` date. Warn, not error, on the first release: the engine has no way to know how much backlog a given vault carries, and a gate that is red on arrival is the always-red-check-gets-bypassed failure this engine has already fixed twice elsewhere (`vault-worktree.sh` records both). Give it `--strict` like `lint-memory.sh` has, so a vault that has drained its backlog can promote it to a gate itself. Do not count generated blocks — the Projects and Skills splices are derived, and their fix is at the frontmatter (see (c)).
- (b) **`bin/lint-always-on.sh`** — over the vault's `CLAUDE.md`: report the word count of each `##` section and fail above a per-vault budget read from the existing vault seam (`$WIKI/.wiki-gates.conf`), with no engine default, because the right budget is a consumer decision and an engine-chosen number would be wrong for every vault. Absent a declared budget it reports the counts and passes — a measurement, not a verdict. This is the same seam shape `lint.sh` already uses for its check 9 (per its own header comment: the engine composes it, the vault fills it in).
- (c) **Add a word cap to `lint-summary-volatility.sh`** — `SUMMARY_MAX_WORDS`, default 25, applied to `done` pages as well, because `summary:` is identity and identity does not freeze differently by status. Keep the existing state-marker heuristic exactly as it is; this is one more condition, not a rewrite.
- (d) **State the hook rule in `SCHEMA.md`**, one sentence beside the existing `summary:` rule at line 62, so the two always-loaded surfaces are documented where the derived one already is: *a hook is one clause stating the rule or the fact; dates, counts and correction history belong in the note.*
- (e) Wire (a) and (b) into `bin/lint.sh` as named sections, so a vault gets them on its next pin bump with no per-vault wiring.

Alternatives considered:

- **Leave it as prose and rely on the model.** Rejected on measured evidence, not preference: a vault that wrote the rule into its own always-loaded file still accumulated 361 over-length hooks and 31 dated ones, and re-measured its own budget by hand three times. The rule was available every time it was broken. That is the same argument the engine already accepted for `prove-the-test-can-fail` — a rule you must remember is weaker than a procedure you run.
- **Make (a) an error immediately.** Rejected: any vault with existing hooks fails its own pre-commit on arrival, on content unrelated to the commit, which teaches `--no-verify`. Warn plus `--strict` lets the vault choose when it becomes a gate.
- **Have the lint rewrite the hooks.** Rejected: a hook is prose, a truncation at 25 words is not a rewrite, and cutting a clause that exists *only* in the hook loses a fact. The lint must report and stop; the trim is a judgement call for a session with the note open.
- **Fold the hook check into `lint-links.sh`**, which already walks `index.md`. Rejected: that script's job is resolution, its output is per-link, and a word-count finding there would be filed under the wrong heading. A separate script keeps `lint.sh`'s section names honest about what failed.

Acceptance criteria:

- `bin/lint-index-hooks.sh --wiki DIR` exists, exits 0 on a vault whose hooks are all within budget, and names the file, line number and word count of each hook over the threshold. Control: it must report a **different** count on two vaults with different hook lengths — a check that reports the same number regardless of input is measuring nothing.
- Red before green, on the subject not the assertion: append one 40-word hook with a `2026-01-01` in it to a fixture `index.md`, run the check, require a non-zero exit under `--strict` naming that line; restore, require green. Then the near-miss: a 24-word hook with no date must NOT be flagged, and a hook whose *note body* contains a date must NOT be flagged (the rule is about the hook line, and a check that reads the note instead would pass its own obvious test and fail on every real vault).
- `lint-always-on.sh` prints per-section word counts and passes when no budget is declared; with a budget declared in `.wiki-gates.conf` below the current count, it fails and names the section. Control: with the budget above the count it passes, so the failure is attributable to the number and not to the file being read at all.
- `lint-summary-volatility.sh` flags a 40-word `summary:` on a `status: done` page. Control: today that page is skipped entirely, so the existing behaviour is a demonstrable pass on the same input.
- `SCHEMA.md` states the hook rule; `lint.sh` runs both new checks as named sections; `lint.sh --help` lists them.
- Neither new script reads anything outside the vault root it is given, and neither embeds a consumer's strings — the engine's own rule at `bin/lint.sh` line 32.

Redactions: the consumer vault's name, its `index.md` content and the text of any individual hook are not reproduced; only the aggregate counts (567 hooks, mean 32.4 words, 361 over 25, 31 dated, longest 164 words) and the fact that its `CLAUDE.md` carries a hand-maintained budget. Nothing was omitted for being awkward to scrub. The measurements come from one vault, on one date, and the thresholds proposed above are engine defaults rather than that vault's numbers.

Instruction to engine-dev: this adds two checks and one condition to a third, all warn-first, so it does not need the full design pass — but it DOES touch `lint.sh`, which doubles as a write-time gate, so run the diff-review gate before pushing. The one real design question is (b)'s seam: whether a per-section budget belongs in `.wiki-gates.conf` beside the denylist or in its own file. Decide that against how `lint.sh` already composes check 9. Create the project under this slug, build, ship.
