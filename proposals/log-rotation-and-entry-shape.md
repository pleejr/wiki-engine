HANDOFF — engine improvement proposal slug: log-rotation-and-entry-shape boundary: generic (engine-domain; contains no consumer-private context)

Title: The engine states a one-dated-line `log.md` entry shape in three places, measures it nowhere, and provides no rotation — so the file grows without bound while the stated rule stays dead and the RAG chunker's tuning silently goes out of date

Engine version: v1.73.4 — the tag this vault is pinned to. Engine line references and the consumer measurements below were taken on 2026-09-03. The pin is one commit behind the engine's `origin/main`, not equal to it.

Problem (generic — true for any consumer vault, and it has two halves that must not be conflated):

1. **The stated rule.** `skills/checkpoint/SKILL.md` line 32 says "Append one dated line to `$WIKI_PATH/log.md`, tagged with the project". `skills/skill-candidates/SKILL.md` line 31 says "`log.md` — one dated line per session". `scaffold/log.md.tmpl` seeds exactly one `- **{{DATE}}** — …` line. Three surfaces, one rule, consistent with each other.

2. **Nothing measures it, in any script.** `bin/lint-links.sh` line 21 and `bin/lint.sh` line 132 *exclude* `log.md` from link lint deliberately (it is history, and history holds retired slugs) — which is correct, and is also why nothing else looks at the file either. `bin/lint-summary-volatility.sh` exists for the analogous `summary:` rule on project pages, so the engine has already accepted that a stated shape rule earns a mechanical check; `log.md` did not get one.

3. **So the rule is dead, and has been from early on.** Measured on one consumer vault, 2026-09-03: 443 entries, 147,556 words, 1.04 MB in a single file. Words per entry: median 331, maximum 898, **433 of 443 over 60 words and 299 over 250**. Ten entries out of 443 obey the stated rule. That is not drift — a rule obeyed by 2% of its population was never in force, and every checkpoint has therefore decided the entry shape afresh. This is the load-bearing observation, and it is the one an engine-dev end can act on without any of the rest.

4. **There is no rotation and no plan for one.** `grep -il 'rotate|archive' bin/*` matches nothing that rotates a log (`reflow.sh` is soft-wrap, `upkeep.sh`'s hit is `reflog`, `crossover.sh`'s is tombstones). A vault's history is append-only by design and correctly so — but an append-only single file is a *file-size* problem, not a history problem, and the two have different answers.

5. **A second consumer of the file is already tuned to a size the file has outgrown, which is the part that fails quietly.** `bin/rag_chunk.py` lines 99-103 pack a flat list page by entry (`LIST_PACK`, deliberately below `MAX_CHARS`), and line 102 records the corpus it was tuned against verbatim: "Measured on a real log: 187 self-contained entries, median 1,475 characters, packed ~2.9 to a chunk at a median 5,115." The same vault today: 443 entries, median ≈2,400 characters. The chunker still runs, still returns hits, and reports nothing — so this is fail-open. Nobody sees a chunker whose packing assumption has doubled out from under it; they see recall that is a bit worse than it was, with no event to attribute it to. **Not verified:** whether the current median actually degrades retrieval quality, or by how much. That needs a recall comparison the consumer side did not run, and it is the question intake should settle before sizing any fix — the observation is that the tuning constant no longer describes the corpus, not that recall is measurably broken.

6. **Ordering is not monotonic, and the cause is structural.** In the same vault the file opens with 38 entries running newest-first, then restarts and runs oldest-first, with four further inversions inside the chronological run. That is the expected signature of concurrent sessions each appending in their own worktree and reconciling by merge — so any rotation keyed on "entries older than X" must read the DATE in each entry, never the position in the file. A rotation that assumes file order is chronological would archive the wrong entries on any vault that runs concurrent sessions, which is every vault the worktree tooling exists to serve.

Motivating use case (generic): a vault has run daily for months. Its history file is now a megabyte, loaded by any tool that reads it whole, chunked by a component tuned for a quarter of its current entry size, and shaped by a rule none of its entries follow. The operator wants the stated rule to be either true or replaced, and the file to stop being the one artifact in the vault with no size story.

Proposed shape — four parts, deliberately separable, because part (a) is a decision and the rest are mechanism:

- (a) **Decide the rule and state it once.** Either change the stated shape to what is practised (a short entry, ≤N words, with links to the notes distilled — and then say so in `SCHEMA.md`, `checkpoint` line 32, `skill-candidates` line 31 and the scaffold template together), or keep "one dated line" and ship (b) as a gate that makes it true. **Do not ship (b) without settling (a)** — a lint enforcing a rule the engine has decided to abandon is worse than no lint. The evidence favours the first: 2% compliance across 443 entries, over months, by sessions that had the rule in context, is the same signal the engine read as "the rule is not the mechanism" when it built `prove-the-test-can-fail`.
- (b) **`bin/lint-log.sh`** — warn on an entry over `LOG_ENTRY_WARN_WORDS` (default whatever (a) settles), warn on a non-monotonic date, and error on an entry whose header does not match the template shape. Warn-first for the same reason as every other new check here: an arriving vault has a full backlog, and an always-red gate teaches bypass. `--strict` to promote it.
- (c) **`bin/rotate-log.sh`** — move entries whose own parsed date is older than the current quarter into `log/<YYYY>-Q<n>.md`, leave a one-line pointer at the top of `log.md`, and never alter entry text (it is history; rotation moves bytes, it does not edit them). Two hard constraints the design must carry: the live file must stay at the path `log.md`, because `skill-candidates` and `rag_chunk.py` both name it literally; and the archive must land under a path the RAG builder already walks. Verified 2026-09-03 by reading it rather than assuming: `bin/rag-build.sh` line 120 globs `**/*.md` recursively under the vault root, and line 120-121's filter skips only the name `engine` and any dot-prefixed path segment (`SKIP_NAMES` at line 64, with the class rule explained at lines 56-63), so a plain `log/` directory is walked. An archive file with no frontmatter also survives the boundary filter, because that filter is conditional on a boundary being present. Idempotent and safe to re-run: a second run on an already-rotated file must move nothing, because a repair path that degrades on retry is worse than the failure it repairs.
- (d) **Re-tune or parameterise `bin/rag_chunk.py`'s list packing** against a current corpus, and record the corpus it was tuned on in the same comment, with a date — so the next reader can tell a stale constant from a current one. This is the item that needs a measurement first (see 5): do not resize a constant on the strength of a median alone.

Alternatives considered:

- **Rotate by line count or file size.** Rejected: the file is not in chronological order (item 6), so any positional rule archives arbitrary entries. Parse the date.
- **Split the log per project instead of per quarter.** Rejected: the log's value is that it is the one chronological cross-project record; per-project history already exists on the project pages, and a per-project split makes "what happened that week" unanswerable — which is the only question the file is uniquely good at.
- **Delete or summarise old entries.** Rejected outright: it is an incident record. Rotation moves it; nothing edits it.
- **Leave the size alone, since the file is only read by tools.** Rejected: one of those tools is a chunker whose packing constant is now off by 1.6× on entry size, and the failure mode is degraded recall with no error — the shape that gets found late or not at all.
- **Ship (b) and (c) and leave the rule ambiguous.** Rejected: see (a). The lint's threshold IS the rule; shipping the lint without deciding the rule just relocates the ambiguity into a default value.

Acceptance criteria:

- `SCHEMA.md`, `checkpoint`, `skill-candidates` and `scaffold/log.md.tmpl` state ONE entry shape, and it is the shape (b) enforces. Control: today those four agree with each other and disagree with 98% of the entries in a real vault, so agreement among the docs is not evidence the rule is live — the check has to be against entries.
- `lint-log.sh` flags an over-length entry and a date inversion, and passes a conforming file. Red before green on the subject: insert one over-length entry into a fixture log, require a non-zero exit naming its date; restore, require green. Near-miss: an entry one word under the cap must NOT be flagged, and an entry whose *body* contains an older date in prose must NOT be read as a date inversion — a check keying on any date in the entry rather than the header date passes the obvious test and fails on real history.
- `rotate-log.sh` on a fixture spanning three quarters leaves the current quarter in `log.md`, writes the older two to `log/<YYYY>-Q<n>.md` byte-for-byte unchanged (`diff` the concatenation against the original), and a second immediate run moves nothing and exits 0.
- After rotation, `bin/rag-build.sh` indexes the archive: a recall query for a string that exists only in a rotated entry returns it. Control: the same query before the rebuild returns nothing, so the positive is attributable to the reindex and not to the string having been findable all along.
- `bin/rag_chunk.py`'s `LIST_PACK` comment names the corpus and the date it was measured, so the next reader can tell a stale constant from a current one without re-deriving the corpus.
- Nothing in the new scripts names a consumer's vault, project or repo strings.

Redactions: no entry text, project name, repo name, ticket key or figure quoted from any entry is reproduced here — only aggregate counts (443 entries, 147,556 words, median 331 words, max 898, 433 over 60 words, 299 over 250, 38 prepended entries, four inversions) and the two engine constants they are compared against. Nothing was dropped for being awkward to scrub. All consumer figures are from one vault on one date.

Instruction to engine-dev: (a) is a decision and blocks (b) — settle it first and record it in the project's Key decisions with the compliance measurement as the reason. (c) touches an on-disk contract (the path other components name literally) so it earns the full design pass and the diff-review gate; re-check the `rag-build.sh` glob and skip-rule claim yourself rather than on this report's word. (d) needs a recall measurement before any constant moves — treat item 5 as an observation with an explicitly unverified consequence, not as a sizing brief. Create the project under this slug.
