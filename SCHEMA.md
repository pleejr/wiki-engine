# SCHEMA — wiki-engine

The spec for an LLM-Wiki (Karpathy pattern) + Kosuri code-adaptation, maintained **in-session by Claude Code** (first-party, plan-covered — no orchestrator). This is the engine: the node model, page conventions, and skills that any wiki vault consumes. It holds **no content** — a wiki repo pins this engine as a submodule and applies these conventions to its own pages.

Each consuming wiki declares its own boundary in its top-level `CLAUDE.md` (see below); the engine is boundary-agnostic.

## Boundary law (convention)

- Every page carries `boundary:` (`personal` or `work`) in frontmatter. A vault holds **no secrets** (keys, credentials, tokens, SSNs, card/bank numbers) and uses a single declared git identity. Crossover between vaults is a deliberate manual export, never automatic.

## Three layers

- **Layer 1 — `raw/`**: captured sources. `articles/`, `papers/`, `transcripts/`, `assets/` are **immutable** ingested docs (carry `source_url`, `ingested`, `sha256`; never edited after capture). `sessions/` is the exception: **disposable** auto-capture scratch written by `rag-capture.sh` (see below) — promote keepers, then prune.
- **Layer 2 — wiki pages**: agent-owned, synthesized (folders below).
- **Navigation**: `index.md` (sectioned catalog + generated skills list) + `log.md` (the chronological log). **A log entry is one dated entry per session, one physical line** — `- **YYYY-MM-DD** — …` or `- **YYYY-MM-DD (tag)** — …` — linking the notes the session distilled; `bin/lint-log.sh` errors on any other bullet shape and warns over `LOG_ENTRY_WARN_WORDS` (default 400, the measured 90th percentile), on an entry that links nothing, and on a date inversion (`--strict` fails). The rule says *entry*, not *line*, because "one dated line" was stated on three surfaces and obeyed by 2% of entries — the number is the rule. The file is append-only and never edited; `bin/rotate-log.sh` moves entries older than the current quarter, byte for byte and keyed on each header date (never position — concurrent sessions merge out of order), into `log/<YYYY>-Q<n>.md`, which the RAG builder walks, leaving one pointer line under the title. `log.md` stays at that path; the tools that read it name it literally.

## The four node types — one graph, the RIGHT freshness each

| Node | Folder | Source of truth | Freshness trigger | Kept current by |
|---|---|---|---|---|
| **repo** | `repos/` | external repo (drifts) | git **ref/SHA** change | LLM re-ingest (`wiki-repo`) |
| **project** | `projects/` | your work (curated) | your **activity** | in-session `checkpoint`; index buckets = deterministic frontmatter **scan** (`bin/gen-projects-index.sh`) |
| **skill** | engine `skills/` | the `SKILL.md` (self-describing, lazy-loaded) | you **edit** it | deterministic frontmatter **scan** (`bin/gen-skills-index.sh`) |
| **memory** | `memory/` | curated note (distilled from raw native memory) | **supersession/contradiction** | **lint** (`bin/lint-memory.sh`) + in-session distill |

Plus general knowledge in `entities/`, `concepts/`, `comparisons/`, `queries/`, and freeform `notes/` (see page conventions).

### Memory is a lifecycle, not just a node
- **Raw** = Claude Code native memory (`~/.claude/projects/*/memory/`) **plus** auto-captured session logs in `raw/sessions/` (from `rag-capture.sh`) — disposable input. Distilled into Curated, **then pruned** (`checkpoint`/`wiki-onboard`, and the `wiki-context` review-and-promote step) so the vault stays the single authority and raw can't drift into a competing source or dilute recall. Never prune before the durable content is captured in the vault.
- **Curated** = `memory/` notes (`type: memory|lesson|decision|preference`) — versioned, linked. The authority.
- **Always-on** = the thin `CLAUDE.md` slice (identity, boundary, how-to-use) — the only front-loaded memory; anything that must load every session lives here, not in native.

## Page conventions

- YAML frontmatter: `title`, `created`, `updated`, `type`, `tags`, `sources`, `boundary`.
- **≥2 outbound `[[wikilinks]]` per page.** A link to a not-yet-written page is a stub marker — a legitimate, permanent part of the model, not a defect. `bin/lint-links.sh` therefore gates only on links that were **meant to resolve**: a dangling target that *nearly* matches a real slug (normalized-equal, within 2 edits, or one slug's hyphen components appearing contiguously in the other's) is an **error** — a typo, or a slug left behind by a rename — while a target resembling nothing stays a warning. Write example links about the syntax itself inside backticks (`` `[[wikilink]]` ``); code spans and fenced blocks are documentation, not links, and are skipped. Targets that must *never* resolve here — another boundary's pages, engine files, skill names — go in the vault's external-refs file so they read as deliberate rather than as rot.
- **Wikilink-valued frontmatter** (e.g. `repos`) must be a **quoted YAML block list**, never an inline value — Obsidian flags inline `[[...]]` in a property as *invalid properties*, and `key: [[a]], [[b]]` isn't valid YAML at all. Write it as a block list of quoted links (`bin/lint.sh` enforces this):
  ```yaml
  repos:
    - "[[some-repo]]"
  ```
- **repo pages** additionally carry provenance for version-keyed refresh:
  ```yaml
  sources:
    - repo: <name>
      ref:  <latest release tag>   # primary freshness signal; the BASE tag only —
                                   # `git describe --tags --abbrev=0`, never the full
                                   # describe form (lint rejects vX.Y.Z-<N>-g<sha>)
      sha:  <HEAD sha>             # fallback for untagged drift
      ingested: <date>
  ```
- **`verified:` — a correctness signal, distinct from freshness** (optional, any page). Freshness (`sources.sha` vs live `HEAD`) only proves *nothing changed since ingest*; it never proves the page was *accurate*. A `verified:` block records that a human or agent actually confirmed the content correct:
  ```yaml
  verified:
    date: <date>        # when it was confirmed
    by:   <who>         # human id or agent (e.g. <human-id> | claude)
    against: <sha>      # for a repo page: the sources.sha the content was confirmed against
  ```
  **Two orthogonal axes:** *fresh* = currency (`sources.sha == HEAD`); *verified* = correctness (someone checked). A page can be fresh-but-unverified, or verified-but-stale.
  **Invalidation is by provenance, not a clock:** for a repo page the stamp is *current* only while `verified.against == sources.sha`. A `wiki-repo` refresh bumps `sources.sha`, which automatically demotes the old stamp to **verified-stale** (re-verify) — so the signal can't silently outlive the content it vouched for, and the check stays offline/deterministic (no live `HEAD` fetch). `bin/verify-status.sh` reports the three states (verified / stale / unverified) and emits the `--todo` work-list.
- **memory notes**: `status: current|superseded`. `superseded` is the one value a script acts on — `bin/lint-memory.sh` exempts such a note from the index-drift warning, so it may leave the map — and it therefore requires **`superseded_by: <slug>`**, one slug naming the successor (a merge that fans out points at a hub page); the lint errors on a successor that is no page in this vault, and on a `superseded` note with no field first **infers** the successor from the record — a link that follows *superseded / replaced / merged into* wording in the retired note, or a note that says it *supersedes* this one — accepting exactly one such candidate (reported, with the line to add) and warning when there are none, two, or one that resolves to no page (fails under `--strict`); a successor field with any other status warns. No `supersedes:` — the inverse is derivable, and a hand-kept inverse drifts. `created:` is checked (warn) because `skill-candidates` counts recurrence by it.
- **project pages**: `type: project`, `status: planned|active|paused|done`, a one-line `summary:` (the index hook), `repos:` (quoted block list, see above); sections Goal · Linked repos · Key decisions (append-only) · Current state (overwritten each session) · Next steps.
  - **`summary:` names IDENTITY, not state** — what the project *is*, stable for its whole life. Current standing belongs to `status:` (which is also the index bucket) and the body's **Current state**. A summary holding a decaying fact ("built, not deployed", "still on v1.2", "blocked on inputs", "paused 2026-07-14") becomes **false through the passage of time with no edit to the page at all**, and because the Projects buckets are generated from `status:`/`summary:`, the index then advertises a state the page's own body contradicts — a false negative in the very artifact meant to summarize project state. It is also duplication: the index already renders standing as the bucket heading the entry sits under. A summary naming no decaying fact cannot decay; that is the rule, and it is what retires the class.
  - **An `index.md` hook is one clause stating the rule or the fact** — what the note *is*; dates, counts and correction history belong in the note. The map is loaded on every turn of every session, so a hook's length is paid by every reader forever while it is written once. `bin/lint-index-hooks.sh` warns over `INDEX_HOOK_WARN_WORDS` (default 25) words or on an inlined date, `--strict` promotes it; `bin/lint-always-on.sh` reports the vault `CLAUDE.md`'s per-section word counts and fails a section over the `always_on_budget_words` the vault declares in `.wiki-gates.conf` (no engine default — the budget is the vault's).
  - **Staleness is derived, and `reviewed:` is how you clear it.** `upkeep.sh scan` queues a project page whose age exceeds a status-appropriate threshold (`UPKEEP_STALE_ACTIVE_DAYS`, default 14; `UPKEEP_STALE_PAUSED_DAYS`, default 90; `done` exempt outright; an unknown status is reported **unassessable** rather than skipped). Age is the newest of `reviewed:`, the page's **git last-commit date**, and `updated:` — derived first, because a hand-maintained field drifts: measured on a real vault, two of three active project pages disagreed with git by three days, in the direction that makes a page *look* stale. Add or bump `reviewed: YYYY-MM-DD` to record "I read this and it is still right"; that is what drains an item without inventing a content edit, and without it the queue could never reach zero. **A fresh clock is not evidence of review** — a bulk reflow bumps the git date with nobody reading the page; only `reviewed:` cannot be satisfied mechanically.
  - `bin/lint-summary-volatility.sh` enforces this as a **heuristic proxy** — a marker list (versions, dates, fractions, state verbs), skipped for `done` pages whose claims are frozen, flagged for everything else including an unknown status. It is deliberately *not* a decision procedure: "identity, not state" is a human judgement, and recall is unbounded — "awaiting the lender's callback" decays exactly as hard and matches nothing. **A clean run means "no listed marker", never "these summaries are stable."** Chronological session work goes to `log.md`, tagged with the project. The `index.md` Projects buckets are **generated** from each page's `status:`/`summary:` (`bin/gen-projects-index.sh`) — closing a project = flip `status: done`, never hand-edit the index. Since v1.77.0 it also warns on a summary over `SUMMARY_MAX_WORDS` (default 25) — on `done` pages too, since identity does not freeze differently by status — and `--strict` promotes that to a failure.
- **skill pages** aren't written by hand — the skills catalog in `index.md` is **generated by scanning** `SKILL.md` frontmatter (`name`, `description`, `status`, `summary`, `updated`) — only fields a script reads; the catalog line renders `summary:`, falling back to the first sentence of `description:`.
- **notes pages** (`type: note`): the low-ceremony home for freeform reference/topic notes that don't (yet) fit a structured node — recipes, how-tos, a vendor you're researching, health notes, and the like. No mandated sections; write freely. **Use `tags:` for the domain** (`[recipe]`, `[medical]`, `[hobby]`, …) so a new life-domain is a new tag, never a new folder. Still carry frontmatter + **≥2 `[[wikilinks]]`** so a note is reachable in the graph. **Graduate** a note to a `concept`/`entity`/`comparison`/`project`/`query` once it earns that structure — `notes/` is the on-ramp, not a junk drawer.
- Provenance: when synthesizing ≥3 sources, append `^[raw/articles/name.md]` to the sourced paragraph.

## Skills (live in this engine's `skills/`; symlinked to `~/.claude/skills/`)

The authoritative list is the **generated catalog in the vault's `index.md`** (`bin/gen-skills-index.sh` scans every `SKILL.md`'s frontmatter; `lint.sh` fails on drift) — this file does not enumerate skills, because a hand-kept subset here went stale at four while `skills/` held twelve. Three families:

- **Vault lifecycle** — stand up and run a vault: `wiki-adopt` (wire a machine), `wiki-onboard` (one-time seed), `wiki-context` (the router: read `index.md`, load on demand), `wiki-repo` (ingest/refresh one repo page), `checkpoint` (end-of-session curation), `crossover` (move pages between vaults), `update` (advance the pinned engine). **In-session only — never a hook.**
- **Engine-dev loop** — improve the engine from a consumer's chair and land it: `engine-proposal` (hand a report upstream; intake it), `drain` (run the queue to empty), `prove-the-test-can-fail` (a new gate must go red first), `skill-candidates` (mine the record for procedures worth a skill).
- **Verification** — `verify` confirms a repo page is *correct* at its recorded sha, distinct from fresh.

Skills resolve the vault from `$WIKI_PATH` (the consuming wiki's root; must be set) and run engine tooling as `$WIKI_PATH/engine/bin/<tool>` — never a bare `engine/bin/` path, which resolves only from the vault root and not from a session worktree or a repo clone.

## Tooling (`bin/`, deterministic — no LLM)

- **`lint.sh`** — the umbrella lint **and the enforced write-time gate** (`checkpoint`, a pre-commit hook, and vault CI all run it): memory notes + frontmatter-property validity (wikilink props must be quoted block lists) + soft-wrap drift + skills/projects-catalog drift + boundary-present + provenance-present + link-integrity + foreign-boundary, aggregated. Run this before committing; exit 1 on any failure. The gates are held **at zero** — a violation fails the write, so there is no backlog of known violations to normalize.
  - **The vault seam is `$WIKI/.wiki-gates.conf`** (optional, `key = value`, **parsed and never sourced**): `external_refs` names link targets that must never resolve here, `foreign_boundary_patterns` names a **git-ignored** file of EREs the vault's pages must not match. Consumer-specific values live in the vault; the engine names none of them. A gate with no patterns file reports `not armed` instead of passing silently, since an unarmed gate and a clean one are otherwise indistinguishable.
    - **A seam file the vault git-ignores is read from the CANONICAL checkout when the linted tree lacks it** (`resolve_seam_file`, `bin/wiki-root-lib.sh`). Git-ignored means structurally absent from every linked worktree, while the `pre-commit` gate lints the worktree and `vault-worktree.sh guard` refuses canonical commits — so without this, a gate configured with per-machine rules reported `not armed` on *every* commit the vault made. The fallback is gated on `git check-ignore`, not on mere absence: a tracked file a branch deleted stays deleted, and a file a tool **writes** (the summary baseline) keeps resolving to the linted tree so a write cannot land outside the branch. Note the deliberate opposition — `resolve_wiki_root` picks the tree a tool WRITES (the worktree), `resolve_seam_file` finds machine-local input it READS (canonical).
- **`gen-skills-index.sh`** — regenerate the `index.md` skills catalog from `skills/*/SKILL.md` frontmatter, spliced between `<!-- skills:start -->` / `<!-- skills:end -->` sentinels. `--check` fails on drift; `--stdout` prints the block. Run after adding/editing a skill.
- **`gen-projects-index.sh`** — regenerate the `index.md` Projects buckets (Planned/Active/Paused/Done) from `projects/*.md` frontmatter (`status`, `summary`), spliced between `<!-- projects:start -->` / `<!-- projects:end -->` sentinels. `--check` fails on drift; `--stdout` prints the block. Run by `checkpoint` (and `lint.sh`) so closing a project can't silently leave the index stale.
  - **Both generators write the working tree they are INVOKED FROM**, not `$WIKI_PATH` (`bin/wiki-root-lib.sh`): explicit `--wiki` wins, else cwd's tree when it is a *different working tree of the same repository* as `$WIKI_PATH`, else `$WIKI_PATH`. `$WIKI_PATH` names the **canonical** checkout while `vault-worktree.sh` exists so a session never writes it, so the older `$WIKI_PATH`-always resolution regenerated the wrong tree's `index.md` from inside a worktree — landing the update outside the branch that required it, and dirtying a tree other sessions share. A retarget says so on stderr; `--wiki "$WIKI_PATH"` restores the old target deliberately. Tools whose data legitimately lives only in canonical — the RAG family (untracked `.rag/`) and the machine/engine-wiring family (`engine/` is a submodule a worktree never populates) — keep resolving `$WIKI_PATH`.
- **`lint-memory.sh`** — validate `memory/*.md`: required frontmatter, valid `type`, ≥2 wikilinks, dead-link and index-drift warnings. `--strict` fails on warnings. This is the memory node's freshness check.
- **`lint-links.sh`** — the link-integrity gate across **all** content-node folders (`lint-memory.sh` sees only `memory/`). Errors on a dangling link that nearly matches a real slug; warns on genuine stubs; ignores links inside code spans/fences and any target in the vault's external-refs file. Root hubs and `raw/` are out of scope — `log.md` is append-only history that legitimately cites pages since renamed or tombstoned, so gating it would make history un-writable.
- **`new-wiki.sh`** — scaffold a new consuming wiki (repo + engine submodule + rendered templates + skill symlinks). Node folders come from `scaffold/node-dirs.txt` (the authoritative framework list).
- **`adopt.sh`** — bring an existing vault up to the engine's current framework: idempotently ensure every `node-dirs.txt` folder exists, **then run `apply-adopt.sh`** to wire any features the pinned engine introduced (hooks etc.). Run after bumping the engine pin (a pin bump updates skills/SCHEMA/bin, **not** vault folders or hooks). `--check` reports missing folders + pending adoption steps without changing anything.
- **`apply-adopt.sh`** — run the `adopt.d/` adoption steps against a vault/machine so a shipped engine feature takes effect **in the next session** without manual `settings.json` surgery. Version-gated by a per-machine marker (`$WIKI/.engine-adopted`, gitignored) — a no-op once the current pin is adopted; `--force` re-runs, `--check` reports pending. Deterministic; always exits 0 (must not block session start). Current steps: wire the `session-boot` hook (`10-…`); repoint `~/.claude/skills/*` at the pinned submodule so skills track the pin, not the cold-start clone (`20-…`).
- **`ensure-hook.sh`** — the add-only primitive the adoption steps call: idempotently ensure a hook command exists in a `settings.json` (jq). Matches by exact command (no dupes), co-locates into **exactly one** existing matcher entry (the first that matches — an event may hold several entries sharing a matcher, and writing to all of them runs the hook once per entry), backs up before any write, never edits/removes an existing hook. Reports on stderr when the command *already* sits in more than one entry that fires for the requested matcher, since add-only can report that but never repair it. `--check` dry-runs. Deterministic; never runs `claude`.
- **`session-boot.sh`** — the engine's **single** SessionStart entrypoint. Wire this one hook and the engine owns the rest: in one pass it runs `apply-adopt.sh` (auto-wire pending features), then `session-preflight.sh` (version staleness; writes the cache), then renders the version banner from that fresh cache and emits one hook-JSON — `systemMessage` (the banner, shown to the **user**, no "hook error" heading) + `hookSpecificOutput.additionalContext` (the adopt/preflight detail, for the **model**). Doing preflight→banner in one process is what keeps the banner current (a separate banner hook raced the cache write). Deterministic; never runs `claude`; always exits 0. `adopt.sh`/`update.sh`/`new-wiki`'s adoption self-wire it (`adopt.d/10-session-boot-hook.sh`).
- **`session-banner.sh`** — pure renderer: prints the one-line version banner text (`wiki-engine <ver> ✓`, or a `⚠` line when stale, plus a `⚠ N other session(s) writing` fragment when the lease registry shows live peers) to stdout. No network, no JSON, no hook semantics — `session-boot.sh` calls it after `session-preflight.sh` writes the cache and delivers the string via `systemMessage`. Instant (engine ver via `git describe`, staleness from the cache, peer count via `lease-lib.sh`).
- **`engine-version.sh`** — report the vault's pinned engine vs latest `origin/main` (deterministic git, no LLM). `session-boot.sh` → `session-preflight.sh` runs it at SessionStart and the banner reports the result; the `update` skill owns the offer-then-update flow. Exit 0 current · 1 update available · 2 offline/error.
- **`doctor.sh`** — one-shot freshness report across *all* consumed components: pinned engine (vs latest tag) + RAG deps + embedding model. Deps go through `rag_deps_check.py`, which separates **actionable** (a *pinned* dep drifted/behind, or a `pip-audit` **vulnerability** anywhere in the RAG closure) from **informational** (transitive "newer available") — so the exit code stays a real signal, not steady-state noise. Reports only. On-demand or from the freshness CI cron.
- **`update.sh`** — apply updates in one step: bump the engine to the latest tag *within the same MAJOR*, `adopt` (which now also wires the new tag's features via `apply-adopt.sh`), re-sync the RAG venv to the pinned deps. **Refuses a MAJOR bump** (needs a reviewed migration); leaves the pin staged, never auto-commits.
- **`reflow.sh`** — normalize Markdown to the soft-wrap convention (one line per paragraph/list item); `--check` flags drift. Word-preserving; leaves frontmatter/code/tables/lists structure intact.
- **`vault-worktree.sh`** — concurrent-session write isolation. `ensure` gives a vault-writing session its own `git worktree` on a `wt/<session>` branch off `origin/main` (own dir + own HEAD, shared `.git`) so two Claude Code sessions can't clobber each other in the single shared `$WIKI_PATH` working tree; `gc` retires stale/orphaned worktrees (clean ones only). `checkpoint` calls it before writing; reads (`wiki-context`) stay on canonical. Deterministic (plain git, no LLM). Opt out with `WIKI_WORKTREE=0`. See "Concurrent-session isolation" below.
- **`lease-lib.sh`** — sourced, never executed: the **single definition** of session-lease liveness (`lease_live`, `lease_finished`, `for_other_live_leases`, `count_other_live_leases`) plus the registry's location and thresholds. `vault-worktree.sh` and `session-banner.sh` both source it. It exists because they are two surfaces answering one question: the banner re-derived liveness from the heartbeat alone and announced provably-finished sessions as live peers, disagreeing with `peers` about the same directory.
- **`rag-setup.sh`** / **`rag-build.sh`** / **`recall.sh`** / **`rag-capture.sh`** — optional **semantic recall + auto-capture** layer (see below).

### Semantic recall (optional RAG layer)

The vault is retrieved index-first by the human-readable map + `[[links]]`; that's lexical + hand-curated. This layer adds a *semantic* one on top so the agent finds pages by **meaning** (a query about "cooling" surfaces a note that only says "thermals") without the user naming pages — they just prompt.

- **Packaged & self-contained.** `rag-setup.sh` creates a **git-ignored venv at `$WIKI/.rag/venv`**, installs a CPU embedder (default `fastembed` + `BAAI/bge-base-en-v1.5` — contextual, 768-dim, quantized ONNX, ~210 MB), prefetches the model into a **durable, machine-global cache** (`${XDG_CACHE_HOME:-~/.cache}/wiki-engine/models`, override with `RAG_MODEL_CACHE`), and writes `.rag/config.json` (recording `lib`, `model`, `dim`, and the resolved `model_cache`). The cache is pinned rather than inherited because `fastembed` otherwise stores weights under `tempfile.gettempdir()`, which the OS reaps on its own schedule while the venv survives — leaving a working runtime that can no longer load its model. `new-wiki.sh` runs it automatically (unless `--no-rag`), so *clone engine → generate vault → recall works* with **no server, no GPU, and nothing external** after the one-time install. Fully offline thereafter. No homelab, no cloud, no secrets. Tunable via `RAG_LOCAL_MODEL` / `RAG_PIP_PKG`: lighter `model2vec` + `minishlab/potion-base-8M` (~30 MB static) or heavier `BAAI/bge-large-en-v1.5` (~1.2 GB). An OpenAI/Ollama endpoint remains available via `RAG_EMBED_API`, but local is the default.
- **Derived, not authoritative.** `rag-build.sh` chunks every page by `##` heading, embeds each chunk in-process via `.rag/venv`, and writes `$WIKI/.rag/index.jsonl` — a **fully rebuildable** sidecar (`rm -rf .rag/index.jsonl && rag-build.sh`). The markdown stays the single source of truth; the index only holds `file:line` pointers back into it. `recall.sh` embeds a query and returns the nearest chunks.
- **Boundary-filtered & incremental.** Skips any page whose frontmatter `boundary` mismatches the vault's; re-embeds only changed files on rebuild.
- **The loop:** `checkpoint` distills markdown → `rag-build.sh` re-indexes → `wiki-context` runs `recall.sh` to auto-load the relevant slice. Optional end-to-end: a vault provisioned with `--no-rag` (or where setup failed on a locked-down laptop) simply has no index and falls back to the map.
- **Hook-safe** in the fork-bomb sense: it runs a small embedding model, never `claude`, and never spawns recursively — but like every skill it runs **in-session, never as a hook**. Backend/model/cache all resolve in `rag_embed.py` — the one seam `rag-setup.sh`, `rag-build.sh`, and `recall.sh` share — from `.rag/config.json` or `RAG_EMBED_API` / `RAG_LOCAL_MODEL` / `RAG_MODEL_CACHE` / `RAG_EMBED_URL` / `RAG_API_KEY`.
- **Curated over raw.** `recall.sh` multiplicatively penalizes `raw/` chunks (`RAG_RAW_WEIGHT`, default `0.80`) so a curated note outranks auto-captured raw at similar similarity — the pile never drowns the good stuff.

### Auto-capture (`rag-capture.sh`)

The memory design's *capture* axis: `rag-capture.sh` appends a metadata entry — timestamp, repo/branch/HEAD, changed file **names**, recent commit **subjects**, optional `--note`; **never file contents, diffs, or secrets** — to `$WIKI/raw/sessions/YYYY-MM.md`, which `rag-build` indexes. The monthly files are **git-ignored, per-machine scratch**: read them from `$WIKI_PATH`, never from a worktree (an ignored file is not checked out into one). Wire it to a Claude Code **SessionEnd** hook; it is deterministic and never invokes `claude`, so it needs no recursion guard (**Hard safety rule**, engine `CLAUDE.md`):

  ```json
  { "hooks": { "SessionEnd": [ { "hooks": [ {
      "type": "command",
      "command": "WIKI_PATH=/path/to/vault /path/to/vault/engine/bin/rag-capture.sh",
      "timeout": 30
  } ] } ] } }
  ```

- **The `timeout` is load-bearing**: a hook that states none inherits the host's short SessionEnd window and is cancelled silently, losing the whole capture (`ensure-hook.sh --timeout N` writes it).
- **The target must be a vault**: the boundary is *asked* of the vault and never defaulted, so a `WIKI_PATH` with no readable `boundary:` is refused by name rather than captured under a guess.
- The full behaviour — workspace-root scanning, the time-bounded activity clauses, repeat suppression, what a capture cannot see, the boundary caveat and the transcript-pointer opt-in — is documented in **`USAGE.md` § Auto-capture in detail** and in the script's own header.

### Concurrent-session isolation (`vault-worktree.sh`)

A vault is one git working tree at `$WIKI_PATH`. Two Claude Code sessions pointed at it share **one HEAD and one set of files on disk** — so `git checkout -b` in one session moves HEAD under the other, and simultaneous edits to the same page are **silent last-writer-wins on disk before git ever sees them** (no conflict, no recovery). This is a filesystem race, not a merge race; a lockfile or `pull --rebase` discipline fixes only the commit step, not the shared editing surface.

- **Fix: a worktree per writing session.** `checkpoint` calls `vault-worktree.sh ensure` before it writes; each session gets its own `git worktree` (own directory + own HEAD, shared `.git`) on a `wt/<session>` branch off `origin/main`. Sessions are then fully independent, and any real overlap surfaces as a **visible merge/PR conflict** on integration instead of silent loss.
- **Always-on, negligible cost.** Isolation is unconditional (not gated on detecting a second session — a missed detection reintroduces the exact clobber). Measured cost is ~0.4 s and <1 MB: only tracked text is checked out. The untracked `.rag/` index and the `engine/` submodule are **not** populated in a worktree — so skills run engine tooling from canonical `$WIKI_PATH/engine/bin/*` (targeting the worktree via `--wiki`) and rebuild RAG against canonical after integrating. Opt out per vault with `WIKI_WORKTREE=0`.
- **Liveness is decided in one place.** A lease is live if its session has not *provably* finished (worktree **and** branch both gone — stronger than the clock, and available immediately rather than `WIKI_LEASE_STALE_MIN` later) **and** its heartbeat is fresh. Both tests live in `bin/lease-lib.sh`, which every surface sources — `peers`, `claim`, `gc`, and the session-start banner — because a registry that shows ghosts stops being read, and the cost is the *next*, genuine warning being ignored.
- **Reads stay canonical.** `wiki-context` is read-only and reads `$WIKI_PATH` directly (a slightly stale HEAD is fine); only the write path needs a worktree. `gc` retires merged/stale worktrees and prunes orphans from crashed sessions, never discarding an uncommitted working tree.

## How a wiki consumes this engine

1. Add this repo as a submodule (e.g. at `engine/`) and pin a SHA.
2. Set `$WIKI_PATH` to the wiki root; symlink `~/.claude/skills/*` to the engine's `skills/*`.
3. Give the wiki a thin `CLAUDE.md` that states its boundary/identity and imports `engine/CLAUDE.md`.
4. Bump the submodule pointer when you want the wiki to adopt a newer engine — updates are opt-in per wiki, so engine changes never silently drift across vaults. After bumping, run `bin/adopt.sh` (creates new node folders **and** wires any new features via `apply-adopt.sh`).
5. Wire the one durable hook once: `session-boot.sh` as a `SessionStart` hook. `adopt.sh`/`update.sh` do this for you (`adopt.d/10-session-boot-hook.sh`) and self-heal it. Thereafter every feature a newer pin introduces auto-adopts on the next session start — no further `settings.json` edits.

### Versioning & migration

The engine is versioned with [SemVer](https://semver.org/) **git tags** (`v1.2.3`), each with a `CHANGELOG.md` entry. `bin/engine-version.sh` (run by `wiki-context` at session start) reports the pinned tag vs latest, classifies the bump MAJOR/minor/patch, and flags MAJOR bumps as breaking. Every push to the engine runs `.github/workflows/ci.yml` — shell-syntax check, soft-wrap check, and a scaffolder→lint→adopt smoke test — so a broken HEAD can't reach a vault's next adopt.

- **PATCH / MINOR — additive** (a fix, or a new node folder / tool / convention): adopt cleanly — bump the pin and run `bin/adopt.sh`. The common case; no migration. A feature that needs *wiring* beyond a folder (a hook) ships an **idempotent, add-only `adopt.d/` step**; `adopt.sh` runs those via `apply-adopt.sh`, and the `session-boot.sh` hook re-runs them on the next session start, so the feature auto-adopts. This is distinct from a MAJOR migration: `adopt.d/` steps only *add* (never remove/rename/rewrite), so they carry no breaking risk.
- **MAJOR — breaking** — removing or renaming a node, or changing the frontmatter schema (e.g. a key rename like `brain:` → `boundary:`) — is **NOT** handled by `adopt.sh` (it only *ensures* folders exist; it never removes, renames, or rewrites content). Each such change needs a **dedicated, idempotent migration** shipped with it (a `bin/migrate-*.sh` or a documented one-time step) and a **major-version tag** so a vault knows the bump is breaking, not routine. Until that migration machinery exists, treat any node removal/rename or schema change as a manual, reviewed migration per vault — never a silent `adopt`.

### Keeping consumed components current

A vault consumes two versioned things: the **engine** (submodule, SemVer tags) and the **RAG runtime** (the `.rag/venv` deps pinned in `scaffold/rag-requirements.txt` + the embedding model). Freshness is layered so *checking* is automatic but *applying* stays opt-in:

- **Per session** — the SessionStart hook (`session-boot.sh`) runs `engine-version.sh` and the banner flags a stale pin; run the `update` skill to advance it.
- **On demand** — `doctor.sh` reports engine + deps + model in one shot; `update.sh` applies engine + dep updates in one step (same-MAJOR only).
- **Automatic (CI, no `claude`)** — Dependabot bumps the workflow actions; a weekly `freshness.yml` cron runs the shared `rag_deps_check.py` (with `pip-audit`) and opens an issue **only when actionable** — a pinned dep is behind or a vulnerability exists — not on routine transitive drift. Neither auto-applies to a vault.

RAG deps are **pinned**, not floating: `rag-setup.sh` installs from `rag-requirements.txt` for reproducibility; bump the file deliberately (the cron/issue is the prompt) and re-provision with `rag-setup.sh --force`. Ingested `raw/articles|papers|transcripts` are immutable snapshots and need no updating.

## Obsidian

Open a wiki repo directly as an Obsidian vault (no conversion). Attachments → `raw/assets/`. Wikilinks + Graph View + Dataview (frontmatter) work natively.

**Line wrapping — soft wrap (one line per paragraph).** Write each paragraph and each list item as a single physical line (no mid-paragraph newlines); separate blocks with a blank line. Keep frontmatter, tables, and fenced code as normal multi-line blocks. This renders as flowing prose in **every** Obsidian view and mode (Reading, Live Preview, Source) with no setting to configure and no per-machine state — the editor soft-wraps long lines on screen. Do **not** hard-wrap prose at a column: Obsidian's default renders each single newline as a break, so column-wrapped text looks broken. `bin/reflow.sh` retrofits an old hard-wrapped vault to this convention (`--check` flags files that would change). `lint.sh` enforces it over **curated** pages and root hubs only — `raw/` is exempt, because its tracked folders hold verbatim sources (reflowing a transcript is corruption, not normalization) and `raw/sessions` is a git-ignored buffer that can never enter the commit the gate protects.
